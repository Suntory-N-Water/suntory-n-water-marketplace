# 統合テストの設計・実装指針

統合テストは、単体テストで扱うビジネスルールに加えて、アプリケーションとプロセス外依存の接続を検証する層として設計する。以下は、このスキルが参照するNotebookLM資料の整理である。

## 用語と範囲

このスキルでは、テスト対象の境界で統合テストを定義する。プロジェクトごとに「統合」の呼び方が違う場合は、名前より境界を優先する。

| 対象 | 主なテスト層 | 検証すること |
|---|---|---|
| ドメインモデル・アルゴリズム | 単体 | ビジネスルール、計算、状態遷移、不変条件 |
| コントローラ・アプリケーションサービス | 統合 | 入力変換、依存の接続、処理の流れ、出力変換 |
| 管理下のDB・ファイルストレージ | 統合 | 本番互換のスキーマ、保存・取得、制約、トランザクション |
| 管理外のHTTP API・メール・メッセージバス | 統合 | 通信境界での要求・応答・メッセージの扱い |
| 重要な利用者シナリオ | E2E | 配備後の主要経路が端から端まで動くこと |

この資料では、単体・統合・E2Eをテスト層として扱う。別システムとの通信仕様は、管理外依存との通信境界を統合テストの対象として整理する。プロジェクトが契約テストを採用する場合は、統合テストとの責務、対象メッセージ、採用理由をスキルやプロジェクト規約に明記する。

## 統合テストに含めるケース

統合テストのケースを作る前に、対象機能・APIまたはユースケース・テスト観点を整理する。機能一覧とテスト観点一覧を組み合わせたテストマップで、どの層で何を確認するかを確認する。

基本の選び方は次のとおり。

- 正常系は、対象のプロセス外依存を一通り通過する最長の代表経路をまず1件選ぶ
- 追加ケースは、プロセス外境界で現れる失敗から選ぶ(DB制約、トランザクション、ネットワーク、外部サービス応答など)
- ドメインルールの境界値・異常値の組み合わせは、原則として単体テストへ割り当てる
- 入力変換・永続化・外部通信など、各テスト層に固有の観点を割り当て、ケース全体の重複を抑える
- 読み取り処理は、複雑な検索・権限・重要な投影など、統合不具合の影響が大きい領域から選ぶ

「1テスト = 1振る舞い」を基本にする。戻り値と処理後の永続状態のように、同じ振る舞いを説明する複数の観察結果は同じテストで確認する。独立した振る舞いはケースを分ける。

## 依存ごとの実物・テストダブルの判断

| 依存 | 基本方針 | 具体的な確認 |
|---|---|---|
| 管理下のDB | 本番と意味が一致する実物または本番互換環境を使う | スキーマ、マッピング、制約、保存後の取得、トランザクション境界 |
| 管理下のストレージ | 可能なら専用の実物または本番互換環境を使う | パス、権限、エンコード、保存後の読み取り |
| 管理外のHTTP・メール・メッセージバス | 内部クライアントではなく通信プロトコルの境界で差し替える | 外部へ渡す要求、応答の変換、失敗時の扱い |
| システム内部のクラス間通信 | 最終的な戻り値・状態・外部境界の結果を検証する | 内部の呼び出し回数・順序は設計判断の補助情報として扱う |

外部へ送る内容そのものが観察可能な仕様なら、要求・ヘッダー・メッセージの構造を具体的に確認する。ログのように内容が仕様へ含まれない場合は、外部境界の結果やアプリケーションの状態を中心に確認する。`vi.mock` や `vi.spyOn` は、管理下のRepository・内部APIクライアントを実物で接続する統合テストと責務が重なるため、通信境界のテストダブルへ置き換える。

## DB・トランザクション・テストデータ

### トランザクションを本番の境界に合わせる

Arrange・Act・Assertは、本番のトランザクション境界を反映する。可能なら準備・処理・確認をそれぞれ独立した接続またはトランザクションから行う(資料では3つに分ける構成を示す)。処理がコミットされた後に、別の読み取りから結果を確認する経路を用意する。

トランザクションのコミット・ロールバック自体が仕様なら、成功時のコミットと失敗時のロールバックを別々の観察可能なケースとして確認する。速度向上のためのロールバックを使う場合は、実際のコミット経路を確認するケースも組み合わせる。

### テスト間の分離

- テストごとに専用のデータ領域、名前空間、または一意な識別子を使う
- Arrangeで必要な前提データを作り、テストスコープ内のcleanupと組み合わせる
- 共有DBを並列実行する場合は、テスト固有の範囲を対象に掃除する
- フレームワークのfixture機能は、失敗時・中断時・並列時の分離を支える形で構成する
- プロジェクトで採用したcleanup方式を統一し、fixtureの読み方を揃える

Vitestを使う場合は、テストのスコープで作成と後始末を登録できる `onTestFinished` や `test.extend` を候補にする。利用できるAPIやプロジェクトのバージョンは、実装前に確認する。

## 非同期処理・ドメインイベント

ドメインモデルがイベントを生成すること自体は、ドメインの観察可能な出力として単体テストで確認できる。統合テストでは、アプリケーションがそのイベントを外部通信へ変換し、必要な境界へ渡すことを確認する。

- 外部へ渡されるメッセージや最終状態を観察対象にし、内部のイベントハンドラ順序は実装上の構成として扱う
- 非同期処理は、観察対象が成立するまでをタイムアウト付きで待つ
- 外部へ送るメッセージの形式が仕様なら、フィールド・値・順序など必要な範囲を明示的に確認する

## 実装前の確認項目

ケース候補をMarkdownで出すとき、統合テストについては次の観点をグループで示す。ケース固有の詳細は、境界やリスクに応じて展開する。

- 対象機能と対象API・ユースケース
- 通過するプロセス外境界(DB、ストレージ、外部通信など)
- 単体テストへ割り当てた観点と、統合テストで担う観点
- 管理下の依存を実物で確認する代表経路
- 管理外の依存を通信境界で扱うケース
- 別の接続・トランザクションから処理後の状態を確認する経路
- 並列実行・失敗時にもテストデータを分離するfixture
- ドメインの異常系を単体テストで確認する範囲
