# テストレビュー・再設計ワークフロー

既存テストを評価し、削除・改善・再設計を行うワークフロー。
「テストを見直して」「不要なテストを探して」「テストが多すぎる気がする」といったリクエストで使用する。

---

## レビューの進め方

既存テストを読み、以下の観点で評価する。
一度にすべてのファイルを処理しようとせず、対象範囲をユーザーと合意してから進める。

### 優先度の分類

各テストを以下の4段階で分類して報告する

| 優先度 | 意味 | 対応 |
|---|---|---|
| 🔴 Blocker | テストスイートに悪影響を与えている(偽陽性・誤ったアサーション) | 即座に修正または削除 |
| 🟡 Major | 価値が低い・保守コストが高い | 削除または書き換えを推奨 |
| 🟢 Minor | 改善できるが機能はしている | 改善を提案(任意) |
| 💡 Suggestion | より良い書き方があるというヒント | 参考として共有 |

---

## 削除候補の特定(🔴 / 🟡)

以下に該当するテストは削除または修正を提案する

| 問題 | 説明 | 影響する柱 | 例 |
|---|---|---|---|
| 実装の詳細を検証している | 内部メソッドの呼び出し順序・回数を検証 | **リファクタリングへの耐性** | `expect(mock).toHaveBeenCalledTimes(3)` で内部手順を確認 |
| 取るに足らないコードのテスト | 1行プロパティや自明なコードのテスト | **退行に対する保護** | getter/setter のテスト |
| スタブを検証している | 入力用のテスト・ダブルへの呼び出しを検証 | **リファクタリングへの耐性** | データ取得用スタブの呼び出し回数を検証 |
| テスト内でドメイン知識を再実装 | 期待値をロジックで算出している | **保守のしやすさ** | `expect(result).toBe(price * taxRate)` |
| private メソッドを直接テスト | テストのために private を public に変更 | **リファクタリングへの耐性** | 内部ヘルパーの直接テスト |
| private 状態を公開してテスト | テストのために内部状態を public に変更 | **リファクタリングへの耐性** | 内部フラグの直接検証 |
| 確認フェーズが空 | テスト対象を実行するだけで何もアサートしていない | **退行に対する保護** | 例外が出ないことだけを確認するテスト |
| カバレッジのためだけに書かれたテスト | 数値目標達成のためだけに存在し、実際の価値がない | **退行に対する保護** | 空の確認フェーズ、自明な正常系の羅列 |
| 契約設計の不変条件が未検証 | 異常系でエラー確認のみ、DB状態の不変を確認していない | **退行に対する保護** | エラーが投げられることだけをアサート |

---

## 改善提案(🟡 / 🟢)

削除ではなく改善が適切な場合

| 現在の問題 | 改善案 |
|---|---|
| 偽陽性が出やすい(リファクタリングで壊れる) | 観察可能な振る舞いのみ検証するよう書き換え |
| AAA パターンに従っていない | Arrange / Act / Assert を空行で分離して構造を整理 |
| テスト名が形式的(`MethodName_Condition_Result`形式) | 「〜の時、〜であること」形式に変更 |
| Act フェーズが複数行 | カプセル化の改善を提案し、Act を1行にできないか検討 |
| コミュニケーション・ベースで書かれている | 出力値ベースまたは状態ベースへの書き換えを検討 |
| 統合テストで内部モジュール(Repository・HTTPクライアント等)をモック | 実物のDBを使う、または外部HTTP通信はHTTPプロトコル境界でモックするよう書き換え |
| テストデータのクリーンアップが漏れている | `beforeEach` + `onTestFinished` パターンに統一 |

---

## 再設計が必要なケース

個別のテスト修正では解決しない、構造的な問題がある場合

- **テストが多すぎて遅い**: 統合テストに重複している単体テストを削除し、テスト・ピラミッドを是正する
- **ドメインロジックの全異常系を統合テストで書いている**: 単体テストに移動し、統合テストはハッピーパスのみにする
- **モックだらけで何をテストしているか不明**: 設計の問題の可能性が高い。アーキテクチャの見直しを提案する
- **テストが壊れやすい(常に偽陽性が発生する)**: 実装の詳細へのカップリングを特定し、観察可能な振る舞いのみを検証するよう書き換える

## レビュー結果の報告

以下の形式で報告する。**「根拠（低下する柱）」は必須**。どの柱が低下しているかを示すことで、なぜ問題なのかが明確になる。

```markdown
## テストレビュー結果

### 🔴 Blocker(即座に対応が必要)
| ファイル:行 | テスト名 | 問題 | 根拠（低下する柱） | 対応 |
|---|---|---|---|---|

### 🟡 Major(削除または書き換えを推奨)
| ファイル:行 | テスト名 | 問題 | 根拠（低下する柱） | 対応 |
|---|---|---|---|---|

### 🟢 Minor(改善を提案)
| ファイル:行 | テスト名 | 現在の問題 | 根拠（低下する柱） | 改善案 |
|---|---|---|---|---|

### 💡 Suggestion
| ファイル:行 | テスト名 | 提案内容 |
|---|---|---|

### 問題なし
| ファイル:行 | テスト名 | 評価 |
|---|---|---|
```

**ユーザーの合意を得てから削除・修正を実行する。**
🔴 Blocker から優先して対応し、🟢 Minor は任意対応とする。
