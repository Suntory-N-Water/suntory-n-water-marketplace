# テストレビュー・再設計ワークフロー

既存テストを評価し、価値・保守性・実行速度を高めるための改善や再設計を行うワークフロー。
「テストを見直して」「価値の低いテストを整理して」「テストが多すぎる気がする」といったリクエストで使用する。

## レビューの確認観点

レビューでは、個々のテストが守る振る舞い、4つの評価項目、ケースの重複・粒度、テスト層の責務、統合テストのデータ分離とトランザクション境界を確認する。価値の低い・重複した・仕様変更で不要になったテストは、根拠を示したうえで削除・統合・書き換えの候補として整理する。

---

## レビューの進め方

既存テストを読み、以下の観点で評価する。対象範囲をユーザーと合意し、優先度の高い領域から進める。

判断する前に、テストの全文に加えて、テスト対象の本番コード・その呼び出し元と呼び出し先・同じ仕様を確かめる他のテスト・CIでどのジョブが実行するか・git の履歴を読む。テストだけを見ると実装寄りに見えても、他に代わりのない取り決めを守っている場合があるため。外部ライブラリの振る舞いに依存するテストは、ライブラリのソースや型定義を直接確認する。

調査の段階ではファイルを編集せず、根拠を報告してから編集に移る。広い範囲を見るときも、確度の低い候補を大量に並べるより、根拠のそろった少数の候補を優先する。

### 対応区分の分類

各テストを、対応の緊急度と改善効果に応じて以下の4段階で報告する。

| 対応区分 | 意味 | 対応 |
|---|---|---|
| 🔴 対応必須 | テストスイートの信頼性を損なっている(偽陽性・誤ったアサーションなど) | 直ちに修正または削除 |
| 🟡 主要改善 | 価値が低い、または保守コストが高い | 削除または書き換えを推奨 |
| 🟢 軽微な改善 | 機能しているが、さらに改善できる | 改善を提案(任意) |
| 💡 提案 | よりよい書き方や設計につながるヒント | 参考として共有 |

## 実装前のMarkdown設計をレビューする

実装前のテスト設計をレビューする場合は、ケースを対象範囲と責務の割り当てとして確認する。

- 対象機能と対象API・ユースケースが、依頼・仕様・既存コードの根拠と対応している
- 機能一覧とテスト観点一覧がテストマップで対応し、抜けと重複を把握できる
- 対象範囲と具体的なテストケース候補が、機能 → API・ユースケース → 観点 → ケースの順に整理されている
- 単体・統合・E2Eの責務が分かれ、各層に固有の観察結果が割り当てられている
- ケース候補が観察可能な振る舞いとして書かれ、実装メソッド名や内部呼び出しから独立している
- 業務例が依頼・仕様・コードの根拠に基づき、不明点が確認事項や補足として示されている
- ID、優先度、理由、Given/When/Thenが、トレーサビリティや合意に価値がある項目へ適用されている
- 統合テスト候補が、管理下の依存・管理外の依存・トランザクション境界の担当を示している

実装前の成果物はMarkdownの候補一覧とし、合意後に責務・fixtureの共有範囲・フレームワークに合わせてテストコードのグルーピングを決める。

## 優先的に改善するテスト(対応必須 / 主要改善)

次の観察結果を、削除・統合・書き換えの候補として評価する。

| 改善対象 | 判断基準 | 改善する評価項目 | 改善の方向 |
|---|---|---|---|
| 実装詳細への結合 | 内部メソッドの呼び出し順序・回数が主な観察結果になっている | **リファクタリングへの耐性** | 公開結果・状態・通信境界のアサーションへ移す |
| 自明なコードへのテスト集中 | 1行プロパティなど、既存保証で説明できるコードが中心になっている | **退行に対する保護** | 独自の振る舞いとリスクのある分岐へ保護を移す |
| スタブの相互作用の確認 | 入力用テスト・ダブルへの呼び出し回数が観察結果になっている | **リファクタリングへの耐性** | スタブは入力提供に使い、出力・状態を確認する |
| 期待値計算の重複 | テスト内でプロダクションと同じロジックを使っている | **保守のしやすさ** | 独立した根拠からリテラルの期待値を置く |
| カプセル化の変更 | テストのためにprivateメソッドや状態を公開している | **リファクタリングへの耐性** | 公開APIで確認し、複雑な責務は抽出してテストする |
| 観察結果の不足 | Act後の戻り値・状態・外部結果へのアサートが不足している | **退行に対する保護** | 振る舞いを表す具体的な期待結果を追加する |
| カバレッジ指標への集中 | 数値の向上がテスト追加の主な根拠になっている | **退行に対する保護** | リスクと振る舞いの保護を追加理由にする |
| 不変条件の確認 | 原子性を持つ更新処理の失敗後状態が観察対象になっている | **退行に対する保護** | エラー結果と処理前後の状態を組み合わせる |
| 1アサーションへの機械的な分割 | 同じ振る舞いの結果を複数テストへ分割している | **保守のしやすさ** | 同じ振る舞いを説明する期待結果を1テストへまとめる |
| 不適切なパラメータ化 | 操作・期待結果・意図が異なるケースを1つの表に混在させている | **保守のしやすさ** | 同一振る舞いだけをパラメータ化し、異なるグループを分ける |

### 価値の低いテストの例

上の表に加えて、次に当てはまるテストを探す。テストを新しく追加するときも、同じ一覧で確認する。

- アサーションがなく、実行して例外が出ないことしか確かめていない
- 値をそれ自身と比較している、または入力をそのまま返すだけの処理を確かめている
- 定数一覧・export 一覧・設定ファイルの内容をテストへ書き写して比較している
- ソースコード・import 文・文字列を検索して、書き方そのものを確かめている
- 公開境界のテストで確認済みの内容を、private な判定関数や呼び出し形で再度確かめている
- 同じ仕様を、同じ条件で複数回呼び出して確かめている
- 共通の処理を、利用側のモジュールごとに同じ内容で確かめ直している
- テスト専用の export・グローバル変数・ラッパーを残すためだけに存在する
- テストからしか呼ばれない本番コードを確かめている
- 期待値を、テスト対象の関数や描画処理そのものを使って作っている
- 確かめたい振る舞いをモック側で実装している、または異なる複数の API を同じモックで代用している
- テスト対象が作るべき結果・順序・コールバック呼び出しを fixture 側で用意している、または本番の処理が書き込まない保存先に対して永続化を確かめている
- 機能フラグの宣言値を読み直すだけで、そのフラグが約束する処理が実際に行われるかを確かめていない
- 失敗することを確かめるテストが、狙った検証とは別の検証で弾かれて通っている、または本番の処理では到達しない拒否を確かめている
- テスト名や fixture が示す内容を、入力が実際には確かめていない(「期間を終了する」という名前で、期間がまだ残っていることを確かめているなど)

振る舞いを変えないリファクタリングで失敗するテストは実装を確かめている疑いがあるが、それだけで削除はしない。次の「残すテストの基準」に当てはまらないことを確かめてから候補にする。

### 残すテストの基準

次の取り決めを、他のテストに頼らず単独で守っているテストは残す。実装寄りに見えても、この取り決めを守る唯一のテストであれば価値がある。

- 公開 API・プラグイン SDK・通信プロトコル・設定・DB 移行・保存形式・セキュリティ・動作環境・既定値・パッケージ・リリース・アーキテクチャの取り決め
- 呼び出し順が利用者から観察できる振る舞いである場合の順序
- どう再発するかを具体的に説明できるバグの回帰テスト
- ソースコードを読んで確かめるテストのうち、利用者に見えるキー・バイト列・パスが変わると失敗し、識別子の名前変更では失敗しないもの。他の方法より安く同じ取り決めを守れるなら残す

実行が遅い、静的な確認しかしていない、という理由だけでは削除しない。残すと判断したテストが現在のコードで失敗する場合は、テストを消す前にプロダクトのバグである可能性を調べ、再現したうえで原因の本番コードを直す。

### 削除前に集める根拠

削除・統合の候補ごとに、編集する前に次の項目を記録する。1つでも埋まらない項目がある候補は、削除せず確認事項として報告する。

| 項目 | 内容 |
|---|---|
| テスト | テスト名とファイル:行 |
| 検出できる失敗 | このテストが実際に検出できる不具合 |
| 本番の呼び出し元 | 対象の本番コードやテスト補助コードを、テスト以外から呼んでいる箇所 |
| 代わりの確認 | 同じ失敗を検出できる、より直接的な層のテスト。代わりが不要ならその理由 |
| 経緯 | git の履歴などから分かる、このテストや差し替え口が作られた理由 |
| 一緒に消せるもの | 削除によって不要になる本番コード・テスト専用 export・テスト補助コード |
| 影響と確認方法 | 削除の影響と、確認に使うテスト実行コマンド |

## 改善提案(主要改善 / 軽微な改善)

次の状態では、既存テストの意図を保ちながら書き換える。

| 観察した状態 | 改善案 |
|---|---|
| リファクタリング時に失敗しやすい | 観察可能な振る舞いへアサーションを移す |
| Arrange・Act・Assertの境界が読み取りにくい | 各フェーズを空行で分け、意図を整理する |
| テスト名から条件と結果を読み取りにくい | 「〜のとき、〜であること」の形で、条件と観察結果を自然な表現にする |
| Actが複数の論理操作に分かれる | カプセル化とテストの振る舞い単位を見直す |
| 外部通信の内容が主な観察結果になっている | 出力値・状態、または通信境界の必要なメッセージ構造へ整理する |
| 統合テストが内部モジュールをテスト・ダブルに置き換えている | 管理下の依存は実物、管理外の通信はプロトコル境界で扱う |
| 統合テストの分離設計が弱い | `references/integration-test.md` に沿って、データ領域・識別子・接続・cleanupを整える |

## 再設計を検討するケース

個別の書き換えより、テスト層や設計の割り当てを見直すと効果が大きい場合

- **統合テストの実行時間が増えている**: 単体テストと統合テストの責務を整理し、各層の代表ケースへ集約する
- **ドメインロジックのケースが統合テストに集中している**: ルールの網羅は単体テスト、統合テストは代表経路とプロセス外境界へ割り当てる
- **統合テストが代表経路に偏っている**: DB制約、トランザクション、外部通信など、プロセス外境界で確認する観点を追加する
- **統合テストがロールバック中心になっている**: コミット後の独立した読み取りと、本番の境界を確認するケースを追加する
- **テストデータの並列実行時分離が弱い**: 専用のデータ領域・名前空間・識別子とcleanup方式を整える
- **テストダブルが多く観察対象が分散している**: 依存境界とアーキテクチャを見直し、公開結果へ観察を集める
- **テストが実装変更に追随して頻繁に失敗する**: 実装詳細への結合を特定し、観察可能な振る舞いへ書き換える

統合テストのレビューでは、詳細な判断基準を `references/integration-test.md` と突き合わせる。

## レビュー結果の報告

以下の形式で報告する。**「根拠(改善項目)」を必ず添える**。どの評価項目を改善する提案かを示すことで、対応の優先度を判断しやすくする。

```markdown
## テストレビュー結果

### 🔴 対応必須(即座に対応が必要)
| ファイル:行 | テスト名 | 観察事項 | 根拠(改善項目) | 対応 |
|---|---|---|---|---|

### 🟡 主要改善(削除または書き換えを推奨)
| ファイル:行 | テスト名 | 観察事項 | 根拠(改善項目) | 対応 |
|---|---|---|---|---|

### 削除・統合候補の根拠
| テスト | 検出できる失敗 | 本番の呼び出し元 | 代わりの確認 | 経緯 | 一緒に消せるもの | 影響と確認方法 |
|---|---|---|---|---|---|---|

### 残すと判断したテスト
| ファイル:行 | テスト名 | 実装寄りに見える理由 | 守っている取り決め |
|---|---|---|---|

### 🟢 軽微な改善(改善を提案)
| ファイル:行 | テスト名 | 現在の状態 | 根拠(改善項目) | 改善案 |
|---|---|---|---|---|

### 💡 提案
| ファイル:行 | テスト名 | 提案内容 |
|---|---|---|

### 確認済み
| ファイル:行 | テスト名 | 評価 |
|---|---|---|
```

**削除・修正の実行前に、ユーザーと対象範囲・対応方針を合意する。**
🔴 対応必須から優先して対応し、🟢 軽微な改善は任意対応とする。

## 削除・書き換えの進め方

- 1回の変更は、同じ本番コードに対応するテストのまとまりに絞る。範囲が広い場合は、まとまりごとに分けて順に進める
- テストを消して不要になったテスト専用 export・グローバル変数・ラッパー・本番の未使用コードは、別名を残さず同じ変更で削除する
- 残す回帰テストは、原因を持つ層のテストファイルへ移す
- 削除したテストと同じ実装を確かめる置き換えのテストは追加しない
- 判断に迷う候補は、削除件数を増やす目的で片付けに含めない。目的はテストへの信頼を上げることで、削除件数ではないため
- 編集後に、対象と同じ本番コードを確かめる周辺のテストを実行する。ソースコードを読んで確かめるテストを消した場合は、そのテストが守っていた取り決めを実際に使うスクリプトやコマンドを実行する
- 報告では、`git diff --numstat` の結果を本番コードとテストコードに分けて示す
