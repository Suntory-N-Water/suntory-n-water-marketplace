# テスト作成ワークフロー

新規テストの作成に使うワークフロー。コード未実装・実装済みの両方に対応する。
「洗い出し → 実装」の2フェーズで進める。

---

## TDD で進める場合

ユーザーが「テスト駆動で」「TDDで」と指定した場合、または新機能を一から実装する場合に適用する。

```
Red   → 失敗するテストを書く(振る舞いの仕様を先に定義)
Green → テストが通る最小限のコードを書く(この時点では汚くて良い)
Refactor → リファクタリングする(テストが守ってくれるので安全)
```

**バーティカルスライスで進める:**
- 1つの振る舞いを表すテスト → 1つの実装 → 繰り返す
- 小さな振る舞いを1本ずつ、テストと実装の短いサイクルで完成させる
- Green フェーズでは「動かす」ことだけを考える。綺麗さは Refactor フェーズで確保する
- テストを書く際は Assert フェーズから書き始める(「何を確認したいか」を最初に決める)
- 古典学派スタイルを採用: ドメインモデルから実装・テストし、上の層へ積み上げる

ここでいう「1つのテスト」は1つの振る舞いを表す単位である。同じ振る舞いの複数の観察結果は、同じテストで確認する。

---

## フェーズ1：テスト観点とケース候補の洗い出し

対象コードを読み、テストすべきケースを特定する。

### コードを4分類する

| 分類 | 複雑さ/重要性 | 協力者の数 | テスト方針 |
|---|---|---|---|
| ドメインモデル / アルゴリズム | 高い | 少ない | **単体テストの最優先対象** |
| 自明なコード | 低い | 少ない | **言語・ランタイム・ライブラリの保証を活用する** |
| コントローラ | 低い | 多い | **統合テストで検証** |
| 過度に複雑なコード | 高い | 多い | **リファクタリングで分割してからテスト** |

- 1行プロパティ、引数なしコンストラクタなど自明なコードは、既存の言語・ランタイムの保証を前提に優先度を下げる
- 過度に複雑なコードは、テストで振る舞いを保護しながら、複雑な責務を分割する設計改善を提案する

### 既存の保証を活用するカテゴリ

次の領域では、プロダクションコードの独自の振る舞いを優先して確認し、言語や外部ライブラリが保証する動作はその保証を活用する。

| カテゴリ | 説明 |
|---|---|
| 言語・ランタイムの保証 | 使用言語やランタイムが仕様として保証する振る舞い(例外送出・配列操作の順序保証・型変換など) |
| 外部ライブラリの内部挙動 | 利用しているライブラリ・フレームワークの実装詳細(ORMのクエリ生成ロジック、テストランナーのアサーション内部動作など) |

### 先に対象範囲を整理する

実装前は、仕様とコードから何の機能をどの境界で確認するかをMarkdownで整理し、その後にテストコードの構造を決める。

- **対象機能**: ユーザーが達成する機能の名前。依頼・仕様・既存コードで確認できる範囲に限定し、未確認の点は質問として整理する
- **対象API・ユースケース**: その機能を実行する操作・入口
- **テスト観点**: 入力、出力、状態変化、エラー、境界、外部通信、永続化など、確認したい切り口
- **テストレベル**: 単体・統合・E2Eのどこで確認するか。境界に応じて選び、各層の責務を割り当てる
- **テストケース候補**: 具体的に確認する振る舞いの一覧。実装手順やfixtureの詳細は、候補の合意後に決める

機能一覧とテスト観点一覧を組み合わせたテストマップを作ると、機能の抜けと、同じ観点が複数のテスト層へ重複するリスクを見つけやすい。

### Markdownで提示する

実装前の出力は、次のような簡潔なMarkdownを標準形にする。対象機能・対象範囲・テスト観点をグループで示し、ケース候補は振る舞いの箇条書きで整理する。ID・優先度・理由・境界・Given/When/Thenは、トレーサビリティや合意に価値がある場合だけ追加する。

```markdown
# テスト設計

## 対象機能

- {依頼・仕様に記載された機能}

## 対象範囲

- API / ユースケース: {対象の操作}
- テストレベル: {必要なレベル}

## テスト観点

- {確認したい観点}
- {確認したい観点}

## テストケース候補

### 単体

- {条件}のとき、{観察可能な結果}になる
- {境界条件}のとき、{観察可能な結果}になる

### 統合

- {入口}から{管理下の依存}を含む代表経路が完了する
  - {プロセス外依存で現れる失敗}を適切に扱う

### E2E

- {重要な利用者シナリオ}を開始から完了まで実行できる

## 補足

- {仕様の確認事項、ケース間の重複を整理する判断など}
```

これは対象機能の中で何を確認するかを合意するための設計メモである。ケースの条件・入力・手順・期待結果を共有すると合意の精度が上がる場合は、そのケースだけ詳細化する。単純なケースは同じ情報をグループで共有し、候補一覧を読みやすく保つ。

### ケース候補と詳細ケースを段階化する

- **候補一覧**: 対象機能・テスト観点・観察可能な振る舞いを、Markdownで短く示す
- **詳細ケース**: 複雑な条件、境界、外部通信、状態遷移など、誤解の余地がある項目に事前条件・入力・手順・期待結果を付ける
- **実装上のテスト**: 合意したケースをfixture、Arrange・Act・Assert、具体的なアサーションへ落とし込む

資料では、実行可能なテストケースの基本要素として事前条件・具体的な入力・実施手順・期待結果を扱う。一方、実装前の候補一覧では、必要なケースだけこの粒度まで展開する。

仕様・データフローが不明瞭な箇所は、確認事項としてユーザーへ提示してから進める。

この段階では、振る舞いの選定と合意に集中する。fixtureやモックの具体的な実装は、ケースの責務と依存境界を確定した後に決める。

**テストケース名の規則:**
- 「〜のとき、〜であること」という形式で振る舞いを明確に表現する
- テストケース名の集合がそのまま機能の仕様書として読めるよう、流暢な日本語で記述する
- 非開発者にも伝わる普通の言い回しで事実を表現する
- テスト名は、利用者が観察する結果と、その条件を中心に表現する
- `「{条件}のとき、{観察結果}になる」` のように、条件と観察結果を自然な日本語で表現する
- 管理下の依存は実物を使い、管理外依存との通信は通信境界を対象にする

条件・観察結果・業務上の意味が後から読めることを優先し、このリポジトリでは上記の形式を標準の書き方として維持する。

### 1テスト1振る舞いのアサーション

1つの振る舞いが複数の公開結果を生む場合は、必要な結果をまとめて確認する。たとえばユーザー登録なら、登録成功と契約上必要なユーザーIDを確認する。正規化済みメールアドレスや初期ロールも公開契約に含まれるなら同じテストに含める。

確認対象は、公開仕様に現れる結果に限定する。実装の内部構造から得た情報は、原因の切り分けやfixtureの確認に使う補助情報として扱う。

テストは振る舞いの単位で分け、同じ振る舞いに属する観察結果は1つのテストへまとめる。結果オブジェクトや値オブジェクトを比較できる場合は、プロパティ単位のアサーションをその比較へ集約する。

### パラメータ化の適用条件

次の条件を満たす場合にパラメータ化する。

- Arrange・Act・Assertの構造が同じ
- 条件が変わっても、確認している振る舞いが同じ
- ケースごとの差分が入力値・期待値・説明だけである

次の場合は、テストグループを分ける。

- 正常系と異常系が混在し、テスト名や期待結果から意図が読みにくい
- Actの操作やAssertの種類がケースごとに異なる
- パラメータが多すぎる、動的に生成される、または表が仕様を隠している

#### ビフォー

正常系と異常系を1つの表に混在させると、1行ごとの期待値は正しくても、テスト名から振る舞いの違いを読み取りにくい。

```typescript
it.each([
  ["有効な値", "abc", true],
  ["空文字", "", false],
])("%s の入力を検証できる", (_, value, expected) => {
  expect(isValid(value)).toBe(expected)
})
```

#### アフター

正常系と異常系を分け、各グループのテスト名を条件と観察結果として読めるようにする。

```typescript
describe("有効な値", () => {
  it.each([
    ["1文字", "a"],
    ["最大長", "abcdefghij"],
  ])("%s のとき、受け付けられる", (_, value) => {
    expect(isValid(value)).toBe(true)
  })
})

describe("無効な値", () => {
  it.each([
    ["空文字", ""],
    ["最大長超過", "abcdefghijk"],
  ])("%s のとき、拒否される", (_, value) => {
    expect(isValid(value)).toBe(false)
  })
})
```

**テスト手法の選定(優先順):**
1. 出力値ベース・テスト(戻り値など、処理が返す結果を検証)
2. 状態ベース・テスト(処理後の利用者が観察できる状態を検証)
3. コミュニケーション・ベース・テスト(管理外依存へ渡す通信内容を、通信境界で検証)

**優先度の判定基準:**
- 高: ビジネス上重要 + 複雑なロジック
- 中: 複雑だがビジネス影響が限定的 / ビジネス重要だが単純
- 低: 補助的な保護価値を持つが、現時点のリスクでは後回しにできる

候補を絞る場面では、ビジネス影響・失敗確率・変更頻度・テストコストを基準に優先度を付ける。トレーサビリティを管理する正式文書ではIDを付与し、通常の実装前メモではグループ見出しで整理する。

**テスト手法の選定:**

- 同値分割・境界値分析: 入力範囲や分類ごとの代表値を選ぶ
- デシジョンテーブル: 複数条件の組み合わせで結果が変わる場合に使う
- 状態遷移: 状態とイベントによって許可される操作が変わる場合に使う
- 組み合わせテスト: パラメータが多い場合に、リスクに応じた組み合わせを選ぶ

手法の採用は、ケースを少数の代表値へ整理できるか、抜けや重複を説明できるかで判断する。

### 契約プログラミングの観点でテストケースを補完する

テストケースを列挙したら、以下の3つの観点でカバレッジを確認する

| 観点 | 説明 | テストケースの例 |
|---|---|---|
| 事前条件 | 関数・メソッドが正しく動作するために、呼び出し側が満たすべき条件 | 引数が null / 範囲外の値が渡された場合 |
| 事後条件 | 正常終了後に必ず成立すべき保証 | 戻り値が期待の型・範囲内にある、副作用が正しく反映される |
| 不変条件 | オブジェクトのライフタイムを通じて常に成立すべき性質 | 処理前後でオブジェクトの整合性が保たれる |

- 事前条件は **入力境界・エラー処理のケース** として整理する
- 事後条件は **正常系の期待結果・副作用** として整理する
- 不変条件は **処理前後の状態を確認するケース** として整理する

**契約設計における検証の徹底:**
- **事後条件**: Actで得た戻り値(出力値)と、副作用がある場合はその後の状態(DBの更新後のレコードをSELECTして確認)の両方をアサートする
- **不変条件**: 更新を伴う操作で仕様が原子性を要求する場合、エラー結果とともに「Act実行前後でDBの状態が保たれること」をアサートに含める

契約プログラミングは、各テスト層で事前条件・事後条件・不変条件を確認するための設計観点として使う。テスト層の選択は、単体・統合・E2Eの責務と依存境界に基づいて行う。

**ユーザーにMarkdownを提示し、合意を得てからフェーズ2に進む。**

## フェーズ2：テストの実装

フェーズ1で合意したMarkdownの対象範囲・テスト観点・ケース候補をベースに実装する。
**ケース候補の意図を保ち、テストコードの `describe` 構造は実装時の責務・fixture・テストフレームワークに合わせて選ぶ。**

> **確認:** テスト実装中に実装の振る舞いと仕様の差異を検知した場合は、テストを続ける前に事実と修正方針をユーザーへ共有する。

### グルーピング構造を決める

グルーピングの粒度はビジネスの文脈とfixtureの共有範囲に合わせる。「このグループを読めばどんな前提条件・シナリオか分かる」という単位を選ぶ。候補の意味に影響する変更は、ユーザーと確認してから反映する。

### テストデータのライフサイクル管理(統合テスト)

テストデータはケース間で独立させ、作成と後始末を同じテストスコープで管理する。共有DBを使う場合は、トランザクション分離、並列実行、失敗時のcleanup、管理下・管理外依存の扱いを `references/integration-test.md` で確認する。Vitestの `onTestFinished` や `test.extend` は、プロジェクトのバージョンと既存のfixture構成に合わせて選ぶ。

### AAA パターンで構造化する

すべてのテストを以下の構造で書く。各フェーズは空行で区切る

```typescript
it("会員ランクがゴールドのとき、20%割引が適用されること", () => {
  const sut = createPricingService()
  const order = createOrder({ memberRank: "gold", amount: 10000 })

  const result = sut.calculateDiscount(order)

  expect(result).toBe(2000)
})
```

### 実装チェックリスト

- [ ] テスト対象は、プロジェクトの命名規則に沿った明確な変数名で表す(`sut`は固有名が適さない場合の既定名)
- [ ] Act フェーズは1つの論理的な操作にまとめ、複数行になる場合はカプセル化とテストの意図を確認する
- [ ] 期待値はリテラルでハードコードし、独立した根拠から導き出す
- [ ] 共通の準備コードは、既存のファクトリ・ビルダー・fixtureを活用し、テストごとの差分を引数で表す
- [ ] 同じ準備・操作・期待結果を持つ同一振る舞いのケースはパラメータ化し、異なる振る舞い・操作・期待結果はグループを分ける
- [ ] プロジェクト内の既存テストユーティリティを活用し、不足する場合だけ追加・改修する

### モックの使用判断

| 依存の種類 | 扱い | 理由 |
|---|---|---|
| 管理下にある依存(専用DB等) | 実物を使い、最終状態を検証 | 実物を通すことでリファクタリングへの耐性を保てる |
| 管理下にない依存(外部HTTP API、メッセージバス等) | HTTPプロトコル境界にテストダブルを置く | 外部との通信という「観察可能な振る舞い」を検証するため |
| 共有依存(テスト間で共有される状態) | テスト・ダブルに置き換える | テスト間の干渉を防ぐ |

内部モジュール(Repository や API Client など)は、管理下の依存として実物を接続する。外部との通信は、HTTPなどのプロトコル境界に置いたテストダブルで差し替える。単体テストでモックが必要になった場合は、依存境界と設計を見直すシグナルとして扱う。

### スタブとモックの区別

- **スタブ**: テスト対象にデータを提供する(入力方向)。戻り値や状態など、テスト対象の観察結果を確認する
- **モック**: テスト対象の出力を検証する(出力方向)。外部通信など、仕様として観察できる内容を確認する

スタブは入力提供に役割を限定し、アサーションはテスト対象の振る舞いに置く。

### テスト実行と修正

テスト実装後、テストを実行して結果を確認する。
失敗したテストがあれば、以下の順で原因を切り分ける

1. テストコードの誤り(期待値の間違い、準備不足)→ テストを修正
2. プロダクションコードのバグ → ユーザーに報告し、修正方針を相談
3. 設計上の改善余地(テストしにくい構造)→ リファクタリングを提案
4. テストと実装の正しさを確定できない → テストを保留し、ユーザーに確認する

全件パスするまでこのサイクルを繰り返す。
