## 機能・テスト観点・テストケースの関係

実装前のテスト設計では、次の階層を分けて扱う。

| 概念 | 役割 |
|---|---|
| 機能 | 利用者が達成したい大きな目的 |
| API・ユースケース | 機能を実行する操作・入口 |
| テスト観点 | 入力、出力、状態変化、境界、外部通信などの確認する切り口 |
| テストレベル | 単体・統合・E2Eなど、どの境界で確認するか |
| テストケース候補 | 条件と観察可能な結果を組み合わせた、具体的な確認単位 |
| 実装上のテスト | ケース候補を実行可能なfixture・操作・アサーションへ落とし込んだもの |

「あるAPI」は対象範囲として扱い、その中に単体・統合・E2Eの責務に応じた複数のテストケース候補を配置する。実装前は、機能一覧とテスト観点一覧をテストマップとして組み合わせ、どのケースをどの層で確認するかを簡潔なMarkdownで示す。

候補一覧は、対象機能・観点・振る舞いを中心に構成する。トレーサビリティを管理する正式なテスト文書ではID・優先度など既存書式を使い、条件が複雑で合意が必要なケースでは前提・入力・手順・期待結果まで展開する。

機能や業務ルールは、依頼・仕様・既存コードで確認できる根拠に基づいて整理する。情報が不足する点は、ユーザーへの確認事項として明示する。

## 「観察可能な振る舞い」と「実装の詳細」の見分け方

リファクタリングへの耐性を備えたテストを書くには、この2つを正しく見分ける能力が不可欠。

### 定義

すべてのプロダクションコードは、クライアント(そのコードを呼び出して使う側のコード)から見て以下のどちらかに分類される。

- **観察可能な振る舞い**: クライアントが自身の目標を達成するために直接的に利用するコード。「クライアントが目標を達成するために使う公開された操作(メソッド)」か「クライアントが目標を達成するために使う公開された状態」のいずれか。
- **実装の詳細**: クライアントの目的達成を支える内部構造。公開されていても、利用者の目標に直接結び付かない要素を含む。

### public な要素も利用者の目標との関係で分類する

テスト対象は、クライアントの目標達成との関係で分類する。公開されている内部ロジックは、利用者の目的に直接結び付く公開操作と区別する。

**具体例1：メソッドの分類** — User クラスに「名前は50文字以内に収める」というルールがあり、文字列を切り詰める `NormalizeName` メソッドが public になっていた場合。クライアント(UserController)の目標は「ユーザの名前を変更すること」であり、「50文字以内に収めること」は内部の制約。`NormalizeName` は public でも実装の詳細として扱い、観察可能な振る舞いは「名前の変更(Name プロパティの更新)」として検証する。

**具体例2：状態からの分類** — MessageRenderer クラスが、内部で使う補助的描画クラスのコレクション `SubRenderers` を public で保持していた場合。クライアントの目標は「HTMLを描画させること(Render メソッドの呼び出し)」であり、補助クラスの構成は内部実装として扱う。

### APIの境界を見極める

クライアントが1つの目標を1つの公開操作で達成できるAPIを基準にする。複数メソッドの順序をクライアントへ要求する場合は、目的に沿った公開操作へまとめる設計を検討する。

### 1テスト1振る舞いの単位

テストの単位は、クライアントにとって意味のある1つの振る舞いである。1つの振る舞いが複数の公開結果を生むなら、複数のアサーションを同じテストに置いてよい。判断の基準は、同じ振る舞いの結果だけを確認していることである。

たとえば「ユーザーを登録できること」を確認するテストでは、登録成功という結果に加えて、ユーザーID・正規化済みメールアドレス・初期ロールが登録処理の公開契約に含まれるなら、それらを確認する。アサーションの対象は、公開契約に現れる結果に限定する。
結果オブジェクトや値オブジェクトの比較は、同じ振る舞いの期待結果を簡潔に表現する手段になる。

### 不変条件とカプセル化

**不変条件(invariant)** — オブジェクトやシステムのライフタイムを通じて成立する条件。公開APIはこの条件を保ちながら、クライアントが目標を達成できる形にする。

「きちんと設計されたAPI」の判断基準：
1. 公開 API が観察可能な振る舞いと完全に一致
2. 実装の詳細をカプセル化して変更可能性を保つ
3. 「尋ねるな、命じよ(Tell, Don't Ask)」の原則に従う

## テスト手法の応用

### 出力値ベース・テストを実現する関数型アーキテクチャ

出力値ベース・テストは、副作用を境界の外へ置いた純粋関数に適用する。ビジネス・ロジックと副作用を分離する「関数型アーキテクチャ」を導入する。

| 構成要素 | 役割 | テスト方法 |
|---|---|---|
| 関数的核(Functional Core) | すべてのビジネスにおける決定を下す。副作用を境界の外へ置いた純粋関数として実装 | 出力値ベースの単体テスト |
| 可変殻(Mutable Shell) | 関数的核に渡す入力データを集め、関数的核が下した決定に基づく副作用を実行 | 少数の代表ケースによる統合テスト |

### 値オブジェクトの活用

値オブジェクト(個別の識別性を持たず、内容によってのみ識別されるオブジェクト)を使うと、状態ベース・テストの品質が向上する。

- **コード量の削減**: 各プロパティを1行ずつ確認する代わりに、期待値となる値オブジェクトを1つ生成し、実際の結果と丸ごと比較するだけで済む(例：`expect(result).toEqual(expectedComment)`)。
- **安全性**: 不変(immutable)であるため、テストケース内でどのように扱っても状態が変わらず、他のテストケースに影響しない。

### 少ないケースで重要な振る舞いを守る手法

入力や状態の組み合わせは、仕様の形に合う手法で代表値へ整理する。

- **同値分割**: 同じ結果になる入力群から代表値を選ぶ
- **境界値分析**: 上限・下限と、その直前・直後を重点的に選ぶ
- **デシジョンテーブル**: 複数条件の組み合わせと結果を表にして、重要な組み合わせを選ぶ
- **状態遷移**: 状態、イベント、許可・拒否される遷移を確認する
- **組み合わせテスト**: パラメータが多い場合に、リスクに応じた組み合わせを選ぶ

手法は、網羅の根拠とケースの重複を説明可能にし、少ないケースで重要な振る舞いを保護するために使う。

## Humble Object パターンとアーキテクチャ

### Humble Object パターン

過度に複雑なコードをテスト可能な形に分割するための設計パターン。

1. 複雑なビジネス・ロジックを別のクラスとして抽出 → プロセス外依存から隔離した「ドメイン・モデル / アルゴリズム」(単体テストが容易)
2. ロジック抽出後に残ったクラス → 連携に集中する質素な「コントローラ」(統合テストで検証)

コードの深さ(複雑さ)と広さ(協力者の数)が分離され、過度に複雑なコードが消滅する。

### ヘキサゴナル・アーキテクチャ

システム全体に Humble Object パターンを適用したアーキテクチャ設計。

| 層 | 役割 | テスト方法 |
|---|---|---|
| ドメイン層 | ビジネス・ロジックを担い、プロセス外依存から完全に隔離 | 単体テスト |
| アプリケーション・サービス層 | ドメイン層と外部アプリケーションとの連携を指揮 | 統合テスト |

## 古典学派とロンドン学派

### 違い

| 観点 | 古典学派(デトロイト学派) | ロンドン学派(モッキスト) |
|---|---|---|
| 隔離の対象 | テスト・ケース自体を他のテスト・ケースから隔離 | テスト対象のクラスを協力者オブジェクトから隔離 |
| 「単体」の定義 | 1単位の振る舞い(複数のクラスにまたがることもある) | 1つのクラス |
| テスト・ダブルの対象 | 共有依存のみ | 不変依存を除くすべての依存 |
| プライベート依存の扱い | 実物のまま使用 | テスト・ダブルに置き換える |

### 推奨：古典学派

古典学派のスタイルを基本とする。理由：

1. **リファクタリングへの耐性を高めやすい** — 観察可能な振る舞いを中心に検証できる
2. **ビジネスの物語を保ちやすい** — 1単位の振る舞いとしてケースを表現できる
3. **設計上の課題を発見しやすい** — 実物の協力者を通じて、複雑な依存関係を観察できる
4. **失敗箇所を短い実行サイクルで絞り込める** — テストを継続的に実行し、直近の変更と結果を対応付ける

## 品質を守る設計選択

### private メソッドのテスト

公開APIを通じて、privateメソッドが生む観察可能な振る舞いを検証する。

- privateメソッドのロジックが複雑な場合は、責務を別のクラスへ抽出し、その公開メソッドとして単体テストする
- O/Rマッパーが呼び出すprivateコンストラクタなど、実質的に観察可能な振る舞いを構成する要素は、プロジェクトの仕組みに合わせて直接確認する

### カプセル化した状態のテスト

テストでは、状態変化がもたらす最終結果(観察可能な振る舞い)を確認する。カプセル化を保ったまま、公開APIや外部から観察できる状態をアサートする。

### テスト期待値の独立性

期待値となる具体的な値(リテラル)をテストコードに置き、テスト対象とは独立した方法(手計算やドメインエキスパートとの確認など)で導き出した結果と比較する。期待値の計算根拠をプロダクションコードから分離することで、同じ誤りの共有を防ぐ。

### 日時などの環境コンテキスト

現在日時はメソッドの引数やコンストラクタを通じて「明示的な依存」として注入し、「値」そのものとして渡す設計を優先する。

### テストしにくさを設計シグナルとして扱う

テストしにくさは、プロダクションコードの構造を見直す合図として扱う。公開APIとfixtureだけでテストを組み立てられる状態を目標に、次の設計改善を検討する。

- ビジネスルールやアルゴリズムを、プロセス外依存から隔離した関数・ドメインモデルへ抽出する
- 外部通信・永続化と、判断を行うロジックを分離する
- 現在日時などの変動する値を明示的に渡す
- 具体クラスの部分モックを増やす前に、責務と依存境界を見直す

テストが内部構造の変更で壊れる場合は、観察可能な結果へアサーションを移せるかを確認する。

### カバレッジの使い方

カバレッジは、テストの届いていない領域やリスクを発見する指標として参照する。数値を確認するときは、保護している振る舞い・観察結果・テストの保守コストと合わせて判断する。

### インターフェイスの導入条件

インターフェイスは、「複数の実装が必要」または「管理外の外部依存を差し替える」責務が生じた時点で導入する。実装が1つで管理下の依存には、具体的な実装を使う選択を基本とする。

## 統合テスト固有のプラクティス

統合テストの設計・実装に関する詳細は [`references/integration-test.md`](integration-test.md) に集約する。判断の要点は次のとおり。

- コントローラ・アプリケーションサービスとプロセス外依存の接続を対象にする
- 管理下のDBやストレージは実物を使い、管理外のHTTP・メール・メッセージバスは通信境界で差し替える
- 正常系はプロセス外依存を通る代表経路から選び、追加ケースは単体テストで扱う領域とプロセス外境界のリスクで決める
- Arrange・Act・Assertは本番の境界に合わせ、コミット後の状態を独立した読み取りから確認する
- テストデータを専用領域・名前空間・識別子で分離し、並列実行と失敗時のcleanupを考慮する
- 戻り値、永続状態、外部へ渡るメッセージなど、クライアントが観察できる結果を検証する

## 複雑なコードをテストしやすくする設計パターン

### CanExecute/Execute パターン

事前条件の確認ロジックをドメインモデルに持たせ、コントローラから条件分岐を取り除くパターン。

```ts
// ドメインモデル側
class User {
  canChangeEmail(newEmail: string): Result<void, Error> {
    if (this.isConfirmed) return err(new Error("確認済みユーザーのメールは変更できない"))
    return ok(undefined)
  }
  changeEmail(newEmail: string): void {
    this.email = newEmail
  }
}

// コントローラ側(条件分岐が消える)
const result = user.canChangeEmail(newEmail)
if (result.isErr()) return result
user.changeEmail(newEmail)
```

**テストへの影響**: `canChangeEmail` の検証ロジックはドメインモデルに閉じているので、出力値ベースの単体テストで徹底的に検証できる。コントローラは統合テストで1件のハッピーパスを通すだけで良くなる。

### ドメインイベント パターン

ドメインモデル内で発生した状態変化をイベントとして記録し、コントローラがそれを受け取って外部との通信(メール送信、メッセージバス等)を実行するパターン。

```ts
class User {
  private _events: DomainEvent[] = []

  changeEmail(newEmail: string): void {
    this.email = newEmail
    this._events.push(new UserEmailChangedEvent(this.id, newEmail))
  }

  collectEvents(): DomainEvent[] {
    const events = [...this._events]
    this._events = []
    return events
  }
}

// コントローラ側
user.changeEmail(newEmail)
for (const event of user.collectEvents()) {
  await eventBus.publish(event)
}
```

**テストへの影響**: ドメインモデルの単体テストでは「イベントが生成されたか(出力値)」を検証するだけで良い。外部との通信のモックはコントローラの統合テストにのみ登場する。
