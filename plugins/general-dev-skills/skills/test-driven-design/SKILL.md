# テスト設計・実装・レビュー スキル

## 核心原則(常に意識する)

テストの価値は4本の柱の **掛け算** で決まる。どれか1つでもゼロなら価値はゼロ。

| 柱 | 意味 |
|---|---|
| **退行に対する保護** | テストでバグをどれだけ検出できるか。実行するコードが多く、ドメインが重要なほど高い |
| **リファクタリングへの耐性** | コードを変えてもテストが壊れないか。実装の詳細に結合すると偽陽性(動いているのに失敗)が生まれ、テストへの信頼が失われる |
| **迅速なフィードバック** | テストが速いほど実行頻度が上がり、バグ発見コストが下がる |
| **保守のしやすさ** | テストを読んで理解できるか、実行・修正しやすいか |

判断に迷ったら以下の優先順位に従う

1. **リファクタリングへの耐性** — 妥協しない。偽陽性はテストスイート全体の信頼を壊す
2. **保守のしやすさ** — 妥協しない
3. **退行に対する保護** と **迅速なフィードバック** — テスト種別に応じて調整

## 「観察可能な振る舞い」の判断基準

テストで何を検証すべきかの判断に迷ったら、この基準を適用する

- **観察可能な振る舞い**: クライアントが目標達成に直接使う公開操作・公開状態
- **実装の詳細**: 上記以外のすべて(public であっても該当しうる)

判別方法: 「クライアントが1つの目標を達成するために、複数メソッドを順番に呼ぶ必要があるか？」
→ Yes なら実装の詳細が漏洩している。テストではなく設計の改善を提案する。

## テスト・ピラミッド

```
     /  E2E  \        ← 最小限。保護と耐性は最大だがフィードバックが遅い
    /  統合   \       ← ハッピーパスと単体で検証できないケースのみ
   /  単体テスト \    ← 最多。ドメインモデル/アルゴリズムを高速に検証
```

すべての層でブラックボックステスト(観察可能な振る舞いのみ検証)を徹底する。

**統合テストの責務:** コントローラ(アプリケーションサービス層)を対象に、実際のDBや外部サービスを使って「全体の流れが正しく動くか」を検証する。ドメインロジックの全異常系は単体テストに任せ、統合テストは重複させない。統合テスト固有の実装パターン(テストデータ管理・トランザクション分離など)は `references/testing-principles.md` の「統合テスト固有のプラクティス」を参照する。

## 作業フロー

### ステップ1: 核心原則を判断軸として確認する

作業を始める前に、以下の3つを判断軸として意識する。

- **4本の柱（掛け算）**: 各テストへの評価コメントは「どの柱が低下しているか」で根拠づける。1つでもゼロなら価値はゼロ。
  - **退行に対する保護** — バグをどれだけ検出できるか
  - **リファクタリングへの耐性** — 実装を変えても壊れないか（妥協しない）
  - **迅速なフィードバック** — テストが速く実行できるか
  - **保守のしやすさ** — 読んで理解・修正できるか（妥協しない）
- **観察可能な振る舞い**: 「クライアントが目標達成に直接使う公開操作・公開状態」のみ検証しているか。SQL・内部メソッド呼び出し・プライベート状態は実装の詳細。
- **テスト・ピラミッド**: 統合テストは「ハッピーパスと単体で検証できないケースのみ」という責務に合っているか。単体テストで検証できる異常系を統合テストで重複させていないか。

### ステップ2: 依頼に対応するファイルを読んで作業する

| ユーザーの依頼 | 読むファイル |
|---|---|
| テストを書く・作る・追加する・TDDで進める | `references/create-test.md` |
| テストを見直す・レビューする・不要なテストを探す・再設計する | `references/review-test.md` |

背景理論・判断に迷った場合は `references/testing-principles.md` も参照する。
