# ADR フォーマット

ADR は `docs/adr/` に置き、通し番号を振ります: `0001-slug.md`、`0002-slug.md`、以下同様です。

`docs/adr/` は遅延生成します。最初の ADR が必要になった時点で作ります。

## テンプレート

```md
# {意思決定の短い表題}

{1〜3文: 文脈、決めたこと、その理由。}
```

以上です。ADR は一段落で十分な場合があります。価値は「意思決定が行われたこと」と「その理由」を記録する点にあり、セクションを埋める点にはありません。

## 任意セクション

以下は本当に価値を加える場合のみ含めます。多くの ADR には不要です。

- **Status** フロントマター(`提案中 | 承認済み | 廃止 | ADR-NNNN により置換`) — 判断を後日見直すときに有用です
- **Considered Options** — 棄却した選択肢を記憶に留めておく価値があるときのみ書きます
- **Consequences** — 自明でない下流の影響を明示すべきときのみ書きます

## 採番

`docs/adr/` を走査し、既存の最大番号に1を加えます。

## ADR を提案する条件

以下の三つがすべて真である必要があります:

1. 巻き戻しにくい — あとで考えを変えるコストが大きい
2. 文脈なしでは意外に映る — 未来の読者がコードを見て「なぜこの方法なのか」と疑問を抱く
3. 実在するトレード・オフの結果である — 別の選択肢が本当に存在し、特定の理由でひとつを選んだ

巻き戻しやすい判断なら書きません。どうせ巻き戻すからです。意外性がなければ、誰も理由を尋ねません。実在の選択肢がなかったなら、「当然のことをした」以上のことは記録しません。

### 該当するもの

- **アーキテクチャの形状。** 「モノレポを採用します」「書き込みモデルはイベントソーシング、読み取りモデルは Postgres に射影します」
- **コンテキスト間の連携パターン。** 「Ordering と Billing はドメインイベントで通信し、同期 HTTP は使いません」
- **ロックインを伴う技術選定。** データベース、メッセージバス、認証プロバイダ、デプロイ先です。すべてのライブラリではなく、差し替えに四半期を要する類のものです。
- **境界とスコープの決定。** 「Customer データは Customer コンテキストが所有し、他コンテキストは ID で参照するに留めます」。明示的な No は Yes と同じくらい価値があります。
- **明白な道からの意図的な逸脱。** 「X の理由で ORM ではなく手書き SQL を使います」。妥当な読者が逆を仮定しそうな箇所です。次の技術者が善意で戻してしまうのを防ぎます。
- **コードから見えない制約。** 「コンプライアンス要件により AWS は使えません」「パートナー API の契約により応答時間は 200ms 未満でなければなりません」
- **棄却した代替案が非自明である場合。** GraphQL を検討し繊細な理由で REST を選んだなら記録します。しないと半年後に誰かがまた GraphQL を提案します。
