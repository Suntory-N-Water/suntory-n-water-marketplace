# ドメインモデリング

設計しながらプロジェクトのドメインモデルを構築・精緻化します。用語に異議を唱え、エッジケースのシナリオを組み立て、判断が固まった瞬間に用語集と意思決定を書き留める、能動的な作業です。単に語彙を参照するために `CONTEXT.md` を読むだけの行為は含みません。モデルを変更するときに使います。

## ファイル構成

多くのリポジトリは単一コンテキストで運用します:

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

ルートに `CONTEXT-MAP.md` が存在する場合、リポジトリは複数コンテキストで運用します。マップは各コンテキストの所在を示します:

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← システム全体の意思決定
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← コンテキスト固有の意思決定
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

ファイルは遅延生成します。書くべき内容が生じたときだけ作成します。`CONTEXT.md` がなければ、最初の用語が確定した時点で作ります。`docs/adr/` がなければ、最初の ADR が必要になった時点で作ります。

## セッション中に行うこと

### 用語集との照合

ユーザーが既存の `CONTEXT.md` の語と矛盾する言葉を使ったら、即座に指摘します。「用語集は『キャンセル』を X と定義していますが、いま話しているのは Y に見えます。どちらですか？」

### 曖昧な言葉を精緻化する

ユーザーが曖昧または多義的な語を使ったら、正確な正規語を提案します。「『アカウント』とおっしゃっていますが、Customer と User のどちらですか？ 両者は別物です。」

### 具体的なシナリオで検証する

ドメイン関係が議論されている場面では、具体的なシナリオで負荷をかけます。境界を精密化させるエッジケースのシナリオを組み立て、ユーザーに厳密な回答を求めます。

### コードとの相互参照

ユーザーが挙動について述べたら、コードが一致するか確認します。矛盾があれば表面化します。「コードは Order 全体をキャンセルしていますが、いま部分キャンセルが可能だとおっしゃいました。どちらが正しいですか？」

### CONTEXT.md をその場で更新する

用語が確定したら、その場で `CONTEXT.md` を更新します。まとめて処理せず、発生した瞬間に記録します。フォーマットは [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md) を参照してください。

`CONTEXT.md` には実装詳細を書きません。仕様書、スクラッチパッド、実装判断の格納場所として扱いません。用語集としてのみ使います。

### ADR は控えめに提案する

以下の三条件がすべて満たされる場合にのみ、ADR の作成を提案します:

1. 巻き戻しにくい — あとで考えを変えるコストが大きい
2. 文脈なしでは意外に映る — 未来の読者が「なぜこの方法なのか」と疑問を抱く
3. 実在するトレード・オフの結果である — 別の選択肢が本当に存在し、特定の理由でひとつを選んだ

いずれかを欠くなら ADR は書きません。フォーマットは [ADR-FORMAT.md](./ADR-FORMAT.md) を参照してください。
