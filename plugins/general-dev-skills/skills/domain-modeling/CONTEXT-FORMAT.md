# CONTEXT.md フォーマット

## 構造

```md
# {コンテキスト名}

{このコンテキストが何であり、なぜ存在するのかを1〜2文で書きます。}

## 用語

**Order**:
{用語を説明する1〜2文}
_Avoid_: Purchase, transaction

**Invoice**:
配送後に顧客へ送る支払い請求です。
_Avoid_: Bill, payment request

**Customer**:
注文を出す個人または組織です。
_Avoid_: Client, buyer, account
```

## ルール

- **意見を持ちます。** 同じ概念に複数の語があるときは、最良のものを一つ選び、他は `_Avoid_` に列挙します。
- **定義は簡潔にします。** 最大1〜2文です。何をするかではなく、何であるかを定義します。
- **このプロジェクトのコンテキスト固有の語だけを含めます。** 一般的なプログラミング概念(タイムアウト、エラー種別、ユーティリティ・パターン)は、プロジェクトで多用されていても含めません。用語を追加する前に問います: これはこのコンテキスト固有の概念ですか、それとも一般的なプログラミング概念ですか？ 前者だけが該当します。
- **自然なまとまりが生じた場合はサブ見出しでグループ化します。** すべての用語が単一の凝集した領域に属するなら、フラットな一覧で構いません。

## 単一コンテキストと複数コンテキスト

**単一コンテキスト(多くのリポジトリ):** リポジトリのルートに `CONTEXT.md` を一つ置きます。

**複数コンテキスト:** ルートの `CONTEXT-MAP.md` にコンテキスト一覧、所在、相互関係を記します:

```md
# コンテキストマップ

## コンテキスト

- [Ordering](./src/ordering/CONTEXT.md) — 顧客の注文を受け付け追跡します
- [Billing](./src/billing/CONTEXT.md) — 請求書を生成し支払いを処理します
- [Fulfillment](./src/fulfillment/CONTEXT.md) — 倉庫のピッキングと出荷を管理します

## 関係

- **Ordering → Fulfillment**: Ordering が `OrderPlaced` イベントを発行し、Fulfillment がそれを消費してピッキングを開始します
- **Fulfillment → Billing**: Fulfillment が `ShipmentDispatched` イベントを発行し、Billing がそれを消費して請求書を生成します
- **Ordering ↔ Billing**: `CustomerId` と `Money` の型を共有します
```

スキルはどちらの構成かを推論します:

- `CONTEXT-MAP.md` があれば、それを読んでコンテキストを特定します
- ルートの `CONTEXT.md` のみ存在すれば、単一コンテキストとみなします
- どちらも存在しなければ、最初の用語が確定した時点でルートの `CONTEXT.md` を遅延生成します

複数コンテキストがある場合、現在の話題がどれに属するか推論します。判別できなければ問い返します。
