# 日本語スタイル検査ルールを 1 本追加する

ユーザーの指摘を受けた同じターンで、個別の表現を 1 本だけ検査ルールへ反映する。禁止語を追加するだけで終わらせず、検出時に自然な書き直し方とテストも持たせる。

## 対象と境界

- 個別の語句・言い回しを、文単位の正規表現で安定して検出できる指摘だけを登録する。
- 「冗長」「意味不明」のような文章全体への評価、主語の大きさ、論理関係など意味理解が必要な指摘は登録しない。理由をユーザーへ返して終了する。
- 文書全体の集計が必要な指摘を、無理に語のルールへ変換しない。
- 会話履歴や既存文書を一括分析して候補を抽出しない。
- 文書の種類ごとに別のルールセットを作らない。ルールセットは 1 つに保つ。

## 先に読むファイル

ルール定義は別タスクで変更されることがある。編集前に、現在の実体を必ず読み直す。

標準位置は `~/.claude/scripts/typescript/style-rules/` とする。移動していれば現行の `style-rules` ディレクトリを探し、別のルールファイルを新規作成しない。

- `rules.json`: ルールの現在のスキーマと登録済みのルール
- `rules.ts`: JSON の読み込み、型、重大度の制約
- `word-check.ts`: 正規表現の適用単位、フラグ、報告件数の上限
- `word-check.test.ts`: 語の検出テストの書き方
- `sanitize.ts`: 文分割、コードブロック、インラインコードの扱い。パターンの境界に影響する場合に読む
- `check.ts`: 書き込み範囲と文書全体の検査範囲。必要な場合に読む

ルールの置き場所・型・テストの入口が変わっていたら、上の名前を盲目的に使わず、現在の実装に合わせる。

## 手順

### 1. 指摘を 1 本のルールへ絞る

ユーザーの指摘から、禁止する文字列、適用条件、言い換え案を取り出す。複数の独立した指摘をまとめて登録しない。既存の `id` と似たルールを調べ、今回の指摘を表す一意な kebab-case の `id` を決める。

登録済みの語句をこのスキル内で例示・引用するときは、必ずインラインコードで囲む。検査対象の語句を地の文に露出させない。

### 2. 機械照合できるか判定する

次の条件を満たす場合だけ、語のルールとして登録する。

- 文字列または限定された前後関係を、正規表現で再現可能に照合できる
- 文脈の意味を解釈しなくても、検出後の扱いを一貫して決められる
- 正常な別の語まで広く巻き込まないパターンを設計できる

条件を満たさない場合はファイルを変更しない。「正規表現では文章全体の評価や意味の判定を再現できないため、今回は登録しない」と理由を説明する。

### 3. 重大度を決める

- `severe`: その文字列が出たら、例外なく違反だと言い切れる場合だけにする。重大な違反は Stop hook によってターンをブロックする。
- `warning`: 用法・引用・仮定・作中人物の認識など、例外の判定に文脈や意味理解が要る場合にする。

ユーザーが強い表現で禁止していても、文字列自体に例外があり得るなら `warning` にとどめる。迷ったら `warning` を選ぶ。

### 4. ルールと書き直し方を設計する

現在の `rules.json` のスキーマに合わせ、次の情報を 1 件分決める。

- `id`: 既存と重複しない短い kebab-case
- `category`: 指摘の分類を表す簡潔な日本語
- `severity`: `severe` または `warning`
- `pattern`: 現在の matcher が受け取る正規表現文字列。正規表現の区切り文字やフラグを勝手に含めない
- `good`: 禁止だけでなく、どう書き直すかを具体例つきで示す。ユーザーが言い換え案を示した場合は、その案をそのまま使う

`word-check.ts` の実装に合わせてパターンを作る。文頭の接続表現だけなら `^` で固定し、部分一致で誤検出する語は否定先読みなどで境界を限定する。正規表現で表現できない意味条件を、曖昧なパターンで代用しない。

### 5. 定義とテストを同じ変更で更新する

1. 現在の `wordRules`（または現行実装で同等の配列）の末尾に、今回の 1 件だけを追記する。
2. `word-check.test.ts` に、そのルールが検出される最小のテストを 1 件追加する。
3. 誤検出しやすいパターンなら、検出してはいけない用例も同じテストに追加する。
4. 既存の順序・書式・ルールを無関係に変更しない。

テストでは、少なくとも検出結果の `ruleId` または一致文字列を確認する。重大度の判断が今回の要点なら `severity` も確認する。コードブロックやインラインコードを除外する実装なら、その境界を壊していないことも確認する。

### 6. 検証する

ルール追加後、定義とテストを確認してから、ルールプロジェクトのルートで次を実行する。

```bash
cd ~/.claude && AGENT=1 bun test scripts/typescript/style-rules/ && bun run lint && bun run type-check
```

`AGENT=1` は Bun の AI エージェント向け出力を有効にし、成功テストの詳細を隠して失敗詳細とサマリーを残す。

失敗したら、新しい定義またはテストの誤りを直して再実行する。テストを削除したり、検査を弱めたりして通過させない。ルールプロジェクトが見つからない場合は、推測で別の場所へ書かず、ユーザーへ確認する。

## 報告

登録できた場合は、登録した語句、`id`、重大度、重大度を選んだ理由、変更した定義・テスト、検証結果を簡潔に伝える。

登録できなかった場合は、ファイルを変更せず、正規表現で安定して判定できない理由を伝える。
