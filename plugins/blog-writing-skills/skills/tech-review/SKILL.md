# 記事の技術的な正しさを確認する

記事の主張が一次情報と観測に支えられているか、コードが書かれたとおりに動くか、読者が自分の環境で再現できるかを確かめる。原稿の書き換えは、依頼された場合だけ行う。

## 読み込む references

| ファイル | 読むタイミング |
|---|---|
| `references/technical-checklist.md` | 手順 1 の前。確認項目の一覧 |
| `../write-blog-article/references/sui-style.md` | 「コードの扱い」「構成」の節。コードブロックと警告ブロックの書き方の規範 |
| `../write-blog-article/references/research-and-validation.md` | 「記録する項目」の節。記録に何が書かれているべきかの基準 |

## 手順

### 1. 確かめる範囲を決める

原稿を読み、次の記述を洗い出す。

- 中心となる主張
- バージョンや時期に依存する記述
- 仕様についての断定
- 動かす前提のコード
- 観測結果として書かれている記述
- 安全性や互換性に関わる助言

### 2. 一次情報を確かめる

検索結果の要約ではなく元の資料を開く。仕様として定められていること、実装の挙動、過去の議論、書き手の推測、意見を区別する。過去の議論が、当時の話として書かれているかも見る。

### 3. コードを確かめる

記事のコードが検証したソースと一致しているか確かめる。すでにある実行環境（`examples/<slug>/` など）を使う。パッケージの追加インストール、外部サービスへの接続、システム設定の変更は、承認を得てから行う。

### 4. 記録と照らす

`research-and-validation.md` の「記録する項目」に照らし、日付、環境、バージョン、成功と判断する条件、観測結果が書かれているか確かめる。未検証の主張に印が付いているかも見る。

### 5. 指摘を返す

`references/technical-checklist.md` の項目ごとに結果をまとめ、下の形式で返す。

## 記事本文と検証用ディレクトリの関係

記事本文には、読者が自分の環境だけで再現できる情報を書く。`examples/<slug>/` は書き手の作業場所であり、読者の手元には届かない。ローカルのパス、ディレクトリ名、そこでの起動コマンド、リポジトリの場所が本文にあれば指摘し、観測した条件と結果に置き換える案を出す。

- 改善前: 「検証用サンプルでは 40 秒でした」
- 改善後: 「キャッシュを無効にした状態で実行したところ、40 秒でした」

## 指摘の形式

重大度の順に並べる。1 件ごとに「場所 / 技術的な影響 / 根拠 / 具体的な修正案」を書く。

```
🔴 修正必須: 短い見出し
場所: contents/blog/2026-09-04_pnpm-setup-migration.md:42
技術的な影響: 読者の環境で何が起きるか、何が動かないか
根拠: 参照した一次情報の URL、または実行して観測した結果
修正案: 具体的な置き換え、追記、削除
```

重大度は `article-review` と同じ 4 段階にする。

| 表示 | 意味 |
|---|---|
| 🔴 修正必須 | 記事が使えない、または読者を誤らせる |
| 🟠 公開前に修正 | 公開までに直すべき技術的な問題 |
| 🟡 改善の提案 | 正確さや再現性が上がる |
| ⚪️ 任意 | 好みの範囲の調整 |

- 同じ問題が繰り返し現れる場合は 1 件にまとめる
- 指摘が 0 件の場合はその旨を伝え、確認できた範囲と、環境の都合で確認できなかった範囲を書く
- 自分で動かして確かめたものと、資料を読んで確かめたものを区別して書く

## 他のスキルへ渡す場面
