# 記事の技術的な正しさを確認する

記事の主張が一次情報と観測に支えられているか、コードが書かれたとおりに動くか、読者が自分の環境で再現できるかを確かめる。原稿の書き換えは、依頼された場合だけ行う。

## 読み込む references

| ファイル | 読むタイミング |
|---|---|
| `references/technical-checklist.md` | 手順 1 の前。確認項目の一覧 |
| `../write-blog-article/references/sui-style.md` | 「コードの扱い」「構成」の節。コードブロック、条件、警告の書き方の規範 |
| `../write-blog-article/references/research-and-validation.md` | 「記録する項目」の節。記録に何が書かれているべきかの基準 |
| `../../references/review-report.md` | 手順 1 と 5。出力先、場所の示し方、件数、重大度、書き換えの扱い |

## 手順

### 1. 確かめる範囲を決める

原稿を読み、次の記述を洗い出す。

- 中心となる主張
- バージョンや時期に依存する記述
- 仕様についての断定
- 動かす前提のコード
- 観測結果として書かれている記述
- 安全性や互換性に関わる助言

観測結果を検証する前に、その結果が起きた条件も抜き出す。OS、ランタイムとパッケージのバージョン、lockfile、`.npmrc` と使用したレジストリ、ネットワーク経路、キャッシュ、環境変数、runner の種類、実行日時、入力、並列度など、結果を左右しうる条件を記事と記録から特定する。

### 2. 一次情報を確かめる

検索結果の要約ではなく元の資料を開く。仕様として定められていること、実装の挙動、過去の議論、書き手の推測、意見を区別する。過去の議論が、当時の話として書かれているかも見る。

引用した文章は、現在の一次情報にそのまま存在するかを確認する。文言が消えた、書き換えられた、リンク先が別の内容になった場合は、commit、blame、変更履歴などでいつ何が変わったかを特定し、現在の事実と過去の記録を分けて書く。過去の引用だけを根拠に、現在も同じ仕様だとは判断しない。

### 3. コードと観測条件を確かめる

記事のコードが検証したソースと一致しているか確かめる。`examples/<slug>/` があれば内容と記事のコードが一致するかを確認し、一致する検証環境が無ければ `sui-blog/examples/<slug>/` に記事のコードを動かす最小限の環境を作る。作成した環境は、実行前に検証記録を置く場所として初期化する。

書き手の観測を検証するときは、まず記事に書かれた条件を揃える。社内 Artifact Registry、self-hosted runner、独自の設定ファイル、特定のネットワーク経路など、手元で揃えられない条件がある場合は、別の環境で結果が違ったことをもって反証しない。「手元の条件では確かめられなかった」として、条件の差を記録する。

パッケージの追加インストール、外部サービスへの接続、push、システム設定の変更は、承認を得てから行う。検証に使った workflow、実行 ID、ログの該当部分は、`examples/<slug>/` の検証記録に残す。

### 4. 記録と後片付けを確かめる

`research-and-validation.md` の「記録する項目」に照らし、日付、環境、バージョン、条件、成功と判断する条件、観測結果、確かめられなかったことが書かれているか確かめる。書き手の観測とレビュー側の観測を分ける。workflow、実行 URL または run ID、ログの該当部分も `examples/<slug>/` に残っているか確認する。未検証の主張には印が付いているかを見る。

検証のために作った使い捨てリポジトリや一時ディレクトリは、証拠を `examples/<slug>/` に保存した後、成功・失敗にかかわらず削除する。削除できたことを確認し、失敗した場合は残っている場所と理由を報告する。既存のリポジトリ、共有ディレクトリ、書き手が指定した場所は削除しない。

### 5. 指摘を返す

`references/technical-checklist.md` の項目ごとに結果をまとめ、`../../references/review-report.md` の出力先、場所、件数、重大度に従って返す。

## 記事本文と検証用ディレクトリの関係

記事本文には、読者が自分の環境だけで再現できる情報を書く。`examples/<slug>/` は書き手の作業場所であり、読者の手元には届かない。ローカルのパス、ディレクトリ名、そこでの起動コマンド、リポジトリの場所が本文にあれば指摘し、観測した条件と結果に置き換える案を出す。

- 改善前: 「検証用サンプルでは 40 秒でした」
- 改善後: 「キャッシュを無効にした状態で実行したところ、40 秒でした」

## 指摘の形式

詳細な指摘は重大度の順に最大 5 件まで並べる。残りは「追加の指摘」にまとめる。1 件ごとに「場所 / 該当箇所 / 技術的な影響 / 根拠 / 具体的な修正案」を書く。場所は行番号だけにせず、見出しと該当箇所の引用で示す。

```
🔴 修正必須: 短い見出し
場所: contents/blog/2026-09-04_pnpm-setup-migration.md > ## セットアップにかかる時間
該当箇所: 「pnpm/action-setup を使うと、セットアップだけで 7 分かかりました。」
技術的な影響: 読者の環境で何が起きるか、何が動かないか
根拠: 参照した一次情報の URL、または実行して観測した結果
修正案: 具体的な置き換え、追記、削除
```

- 同じ問題が繰り返し現れる場合は 1 件にまとめる
- 指摘が 0 件の場合はその旨を伝え、確認できた範囲と、環境の都合で確認できなかった範囲を書く
- 自分で動かして確かめたものと、資料を読んで確かめたものを区別して書く

## 書き換えを依頼された場合

`../../references/review-report.md` の「書き換えの扱い」に従う。一次情報との不一致や実行結果との不一致のような事実の誤りは、確認を待たずに直す。構成、主張の強さ、扱う範囲、書き手の意見を変えるときだけ、先に承認を得る。
