# 技術的な確認項目

`tech-review` の手順で使う。各項目について、確かめた方法（資料を読んだ、実行した、確かめられなかった）を指摘に書く。

## 主張と根拠

- 中心となる主張が、一次情報または記録された観測に支えられているか
- バージョンに依存する事実が、現在の情報と照らして正しいか。CHANGELOG、リリースノート、公式ドキュメントの該当箇所を開いて確かめる
- 引用した文章が現在の一次情報にそのまま存在するか。消失・改変している場合は、commit や履歴で変更時期と現在の文言を特定する
- 1 つの対象で確かめた挙動が、その対象について確かめたこととして書かれているか。同じ仲間から別の対象を 1 つ選んで同じ規則が成り立つかを確かめ、成り立たなければ、対象ごとに成り立つ言い方へ直す案を出す
- 設定やオプションについて、観測できた差分だけが書かれているか。その設定を外した状態で動かして結果が変わることを確かめる。変わらなければ、その設定が足しているのは別の条件である
- 読者への忠告に書かれた理由が、実測で支えられているか。測って理由が成り立たなければ、成り立つ理由へ差し替えるか、忠告ごと削る案を出す
- 仕様として定められていること、実装の挙動、過去の議論、書き手の推測、意見が区別して書かれているか
- 過去の議論が、当時の話として書かれているか。すでに解決した Issue を現在の問題として書いていないか

## コード

- 構文、型、API の使い方が、記載されたバージョンで正しいか
- import、依存関係、環境変数、設定、起動の順序が揃っているか。初めての環境で上から順に実行して動くか
- 記事のコードが、検証したソースと一致しているか
- 期待する出力と、観測した出力が一致しているか
- バージョンに依存する場合、インストールの例でバージョンが固定されているか
- ファイルを作るコードブロックに、言語指定とパス（` ```ts src/example.ts `）が付いているか

## 記録

- 検証した日付、環境（OS、ランタイムとパッケージのバージョン）、実行したコマンド、成功と判断する条件、観測結果が書かれているか
- 記事の適用範囲（対象のバージョン、対象外になるバージョン、情報の時点）と、検証に使った環境が書き分けられているか。適用範囲は導入の直後、検証環境はその結果を示す箇所に置く
- 書き手が観測した条件（レジストリ、`.npmrc`、ネットワーク経路、runner、キャッシュなど）と、レビュー側が検証した条件が区別されているか。揃えられない条件は「確かめられなかった」と記録されているか
- GitHub Actions、Cloudflare Workers、Claude Code のように対象ごとに決まる記録項目が揃っているか（`../../write-blog-article/references/research-and-validation.md` の「記録する項目」）
- workflow、実行 URL または run ID、ログの該当部分が `examples/<slug>/` に残っているか。ログに認証情報が含まれていないか
- 未検証の主張に印が付いているか
- 集計した表の条件（対象、期間、件数、除外したもの）が書かれているか

## 安全性、互換性、再現性

- コードに出てくる認証情報が、ダミーの値か使い捨ての値になっているか
- 安全性、アクセシビリティ、互換性、失敗する条件が、必要な箇所で扱われているか
- 破壊的変更や取り返しがつかない操作に `> [!WARNING]` や `> [!CAUTION]` が付いているか
- 検証のためだけに作った使い捨てリポジトリや一時ディレクトリが、証拠を保存した後に削除されているか。削除できなかった場合は場所と理由が記録されているか
- 記事本文が、読者の環境だけで再現できる情報で書かれているか。ローカルのパス、`examples/<slug>/` のディレクトリ名、検証用リポジトリの場所が本文に残っていないか
