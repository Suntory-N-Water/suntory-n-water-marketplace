# ブログのネタを判定する

素材や作業の記録を読み、「書くだけの材料があるか」だけを判定する。深掘りは `write-blog-article` の 1 回目の合意確認で行うため、ここでは切り口の有無と材料の揃い方を見る。

## 前提

- 対話が前提のスキル。質問を書いたターンはそこで止め、ユーザーの回答を待つ
- 他のプラグインのスキルを呼ばずに単独で動く
- GitHub Issue を作るのは「材料が足りない」と判定したときだけ。「今すぐ書く」は `write-blog-article` へ渡し、「見送る」は理由だけを伝える
- 使うラベルは `neta` 1 種類だけ。状態は Issue の open / closed の 2 値で管理する
- 記録先は、このスキルを呼び出した作業ディレクトリの GitHub リポジトリ

## 参照ファイル

- `references/topic-questions.md`: 入力の種類の判定、質問の作り方、3 つの判定の基準。手順 1 の前に読む
- `assets/neta-issue-template.md`: Issue 本文の形式。Issue を作る直前に読む

## 手順

### 1. 入力の種類を判定する

`references/topic-questions.md` を読み、入力を次の 3 つのどれかに分類する。

| 入力 | 特徴 | 次の手順 |
|---|---|---|
| 素材 | URL とページ本文、記事やドキュメントの引用 | 手順 2 へ |
| 作業の記録 | 手を動かしたときのメモ。コマンド、エラー、詰まった箇所、所感 | 手順 2 へ |
| 記録済みの Issue の一覧 | 「次のネタを選びたい」「何を書くか決めたい」という依頼 | 「Issue から選ぶ」へ |

分類の結果をユーザーに 1 行で伝える。

### 2. 具体的な質問を 1〜2 問だけ行う

素材の固有名詞や数値に紐づけた質問を作る。例: 「7 分かかっていたのは pnpm のインストールですか、依存関係の解決ですか」。質問の作り方は `references/topic-questions.md` に従う。質問を出力してターンを終え、回答を待つ。

### 3. 判定する

回答を `references/topic-questions.md` の基準に照らし、3 つのうち 1 つに決める。

| 結果 | 条件 | 次の動作 |
|---|---|---|
| 今すぐ書く | 記事の型が決まり、主張を支える材料（動かせるコード、実測値、一次情報）が揃っている | `write-blog-article` へ渡す |
| 材料が足りない | 切り口はあるが、検証や調査が済んでいない | `neta` ラベル付きの GitHub Issue に記録する |
| 見送る | 既出である、切り口が見つからず材料も足りない、記事にする理由が見つからない | 理由だけを伝える |

判断に迷う場合は、具体的な質問をもう 1 問だけ行って再判定する。

### 4. 判定の理由を伝える

判定の結果と、どの材料が揃っていて何が足りないかを伝える。

- **今すぐ書く**: 記事の型、切り口、揃っている材料を 3 行で示し、`write-blog-article` へ切り替える。素材と回答は、1 回目の合意確認で使う入力として渡す
- **材料が足りない**: Issue を作り、URL を伝える（下の「Issue に記録する」に従う）
- **見送る**: 見送ると判断したこと、どの材料が足りなかったかの 2 点を伝える。素材の URL はチャットの本文に残す

## Issue に記録する

1. 記録先のリポジトリを特定する

   ```bash
   gh repo view --json nameWithOwner -q .nameWithOwner
   ```

2. `neta` ラベルが無ければ作る

   ```bash
   gh label list --search neta
   gh label create neta --description "ブログのネタ候補" --color "0e8a16"
   ```

3. `assets/neta-issue-template.md` を読み、その形式で本文を組み立てる。ユーザーの発言は、そのままの言葉で引用する。要約や言い換えをしない
4. タイトルは「素材の主題 + 切り口」を 40 文字以内で書く。素材のページタイトルをそのまま流用しない
5. Issue を作る

   ```bash
   gh issue create --title "<タイトル>" --label neta --body-file - <<'EOF'
   <組み立てた本文>
   EOF
   ```

6. 作成した Issue の URL をユーザーに伝える

## Issue から選ぶ

1. open な `neta` Issue を取得する

   ```bash
   gh issue list --label neta --state open --json number,title,body --limit 30
   ```

2. 2〜3 件を選んで提示する。直近に作られたもの、「確かめる必要があること」が具体的に書かれているものを優先する。番号、タイトル、足りないもの 1 行、引用 1 行で示し、全件は列挙しない
3. どれを書くかをユーザーに選ばせ、ターンを終える
4. 選ばれた Issue の本文を渡して `write-blog-article` へ切り替える。Issue に書かれた「足りないもの」と「確かめる必要があること」は、1 回目の合意確認で調査と検証の項目になる。PR 本文に `Closes #<番号>` を書けば、マージ時に Issue が閉じることを伝える

## 困ったとき

- 作業ディレクトリが GitHub リポジトリでない、または `gh repo view` が失敗する場合は、記録先を 1 問で確認し、`--repo <owner/name>` を付けて実行する
- `gh` が未認証の場合は、`gh auth login` の実行をユーザーに求めて止める。組み立てた Issue 本文はチャットに残し、再実行で使えるようにする
- open な `neta` Issue が 0 件の場合は、素材か作業の記録を渡してもらい手順 1 から始める
- 入力が素材でも作業の記録でもなく、すでにテーマが定まった執筆の依頼である場合は、`write-blog-article` へ切り替える
