# sui-blog の記事を書く

記事は `contents/blog/<YYYY-MM-DD>_<slug>.md` に作る。読者が自分の環境だけで再現できる形で、確かめた事実だけを書く。

## 読み込む references

| ファイル | 読むタイミング |
|---|---|
| `references/sui-style.md` | 合意確認の前、執筆の前、最後の見直し |
| `references/article-types.md` | 構成を提案する前 |
| `references/research-and-validation.md` | 外部から確かめられる主張やコードを含む場合 |

規則の本体は references に置いてある。この SKILL.md には手順だけを書く。

## 手順

### 1. 依頼の内容を把握する

ユーザーが渡したファイルと作業場所を先に読む。`references/article-types.md` を読み、4 つの型のどれかに分類する。質問するのは、読んでも分からなかったことだけにする。

### 2. 1 回目の合意確認

`references/sui-style.md` を読んでから始める。次の項目について、1 問ずつ質問して決める。質問には推奨する答えとその理由を添える。曖昧な答えには具体例を出して問い返す。

- 想定する読者と、前提にしてよい知識
- 読者が持ち帰る結論、またはできるようになること
- 扱う範囲と、範囲の外に置くもの
- 調査が必要な主張
- 検証で示す必要のある主張
- 検証する環境と、成功と判断する条件
- 記事の型と、見出しの案
- タイトルの方向、`description` の方向、英小文字の kebab-case による `slug`

すべて決まったら、決定事項、前提、採らなかった選択肢、残っている疑問をまとめて示し、承認を得る。記事のファイルを作るのは、承認を得た後にする。

### 3. 調べて説明する

`references/research-and-validation.md` の「一次情報の調べ方」に従う。仕様、公式ドキュメント、公式のリポジトリ、リリースノート、Issue と Pull Request を優先し、元の資料を開く。分かったことは、驚いた制約や過去からの変更も含めてユーザーへ説明する。根拠が見つからない場合は、根拠を確認できなかったと書く。

### 4. 証拠を用意する

`references/research-and-validation.md` に従い、`sui-blog/examples/<slug>/` で動かして確かめる。主張と観測の対を先に書き出し、日付、環境、条件、観測結果を記録する。手元で動かせない対象で使い捨てのリポジトリを作る場合は、実行前にユーザーの承認を得る。

### 5. 2 回目の合意確認

中心となる主張、集めた証拠、制約と互換性、見出しの案、検証の結果、一次情報を示し、承認を得る。軽い記事の場合、ユーザーはこの確認を省略できる。

### 6. 執筆する

`references/sui-style.md` を読み直してから、`contents/blog/<YYYY-MM-DD>_<slug>.md` を作る。frontmatter は 8 つのフィールドを埋める。

```yaml
title:
slug:
date: YYYY-MM-DD
modified_time: YYYY-MM-DD
description:
icon:
icon_url:
tags:
  -
```

`description` は要約ではなく、背景、行ったこと、記事で扱う範囲を 1〜3 文で書く。検索結果や記事の一覧だけで内容が判断できる形にする。本文と同じ「です・ます」の敬体で書き、文は述語で終える。既存記事の例を示す。

```
GitHub Actions で pnpm v11 を pnpm/action-setup で使うと、セットアップだけで 7 分かかっていました。setup-node のキャッシュと pnpm/setup へ移行して 40 秒まで短くなったので、原因の切り分けと移行の手順を書きます。
```

```
Cloudflare Workers の無料プランで日次のバッチを動かしています。1 年運用して見えてきた制限の当たり方と、そこに合わせた設計を書きます。
```

`diagram` と `selfAssessment` は別のスキルで作る。このスキルでは埋めない。

本文には、読者が自分の環境だけで再現できる情報を書く。`examples/<slug>/` は書き手の作業場所であり、読者の手元には届かない。ローカルのパス、ディレクトリ名、そこでの起動コマンド、リポジトリの場所は記事の外に置き、観測した条件と結果だけを本文に残す。

- 改善前: 「検証用サンプルでは 40 秒でした」
- 改善後: 「キャッシュを無効にした状態で実行したところ、40 秒でした」

### 7. 見直す

`article-review` と `tech-review` を使う。両方が使えない環境では `references/sui-style.md` に照らして自分で確認する。日本語と英数字の間のスペースは textlint の検査対象の外にあるため、手で確認する。

### 8. 報告する

次の項目を報告する。

- 記事のパス
- 記事の型
- 想定読者
- 中心となる主張
- 一次情報
- 検証の記録（日付、環境、コマンド、結果）
- 実行できなかった確認
- 残っている作業

公開、翻訳、コミット、push は、依頼された場合だけ行う。

## 判断に迷ったとき

- 型が 2 つにまたがる場合は、中心となる主張を支える証拠の種類で決める。動かした結果が中心なら型 1 か型 2、集計表が中心なら型 3、自分の判断が中心なら型 4 を選ぶ
- 検証の環境が用意できない場合は、その主張を未検証と明示し、記事を下書きのまま残す
- ユーザーが「ネタになるかまだ分からない」段階なら、`pick-blog-topic` へ切り替える
