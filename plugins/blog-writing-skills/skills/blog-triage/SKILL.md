# ブログネタトリアージワークフロー

素材や作業ログを、書く価値の有無で選別する。書く価値ありと判定したものだけを GitHub Issue に記録し、後日の着手時に当初の熱量とゴールを復元できる状態にする。

## このスキルの前提

- 対話が前提のスキル。質問を書いたターンはそこで止め、ユーザーの回答を待つ。
- Issue を作るのは採用判定のときだけ。見送りは Issue を作らずチャットで伝えて終える。
- 使うラベルは `neta` 1 種類のみ。状態は Issue の open / closed の 2 値だけで管理する。中間ラベルを作らない。
- 記録先は blog-triage を呼び出した作業ディレクトリの GitHub リポジトリ。リポジトリ名をスキル側で固定しない。
- 深掘りは grilling スキルに委譲する。深掘りのロジックをこのスキル内に書かない。

## 参照ファイル

- `references/triage-questions.md`: 入力種別の判定、具体質問の作り方、採用 / 見送りの判定基準(モード A の着手前に必読)
- `assets/neta-issue-template.md`: Issue 本文の出力形式(Issue 作成の直前に読む)

## Step 0: モードを判定する

1. ユーザーの入力に素材本文または作業ログが含まれる場合は、モード A(トリアージ)へ進む。
2. 「次のネタを選びたい」「何を書くか決めたい」など、記録済みネタからの選択を求められた場合は、モード B(ネタ選択)へ進む。
3. どちらとも判断できない場合は、素材を渡したいのか記録済みネタから選びたいのかを 1 問だけ確認する。

---

## モード A: トリアージ

### Step A1: 手順書を読み、入力種別を判定する

1. `references/triage-questions.md` を読む。
2. 入力を「素材本文」と「作業ログ」のどちらかに分類する。分類基準は同ファイルの表に従う。
3. 分類結果をユーザーに 1 行で伝える。

### Step A2: 軽量質問を投げる

1. 分類した入力種別に対応する質問の作り方に従い、素材の中の具体物に紐づけた質問を 1〜2 問だけ作る。
2. 抽象的な質問(「ゴールは何ですか」「何を伝えたいですか」)を投げない。
3. 質問を出力してターンを終え、回答を待つ。

### Step A3: 採用 / 見送りを判定する

1. `references/triage-questions.md` の判定基準に照らして回答を判定する。
2. 判断に迷う場合は、具体的な質問をもう 1 問だけ投げて再判定する。
3. 見送りと判定した場合は、同ファイルの「見送り時の伝え方」に従ってチャットで伝え、**Issue を作らずに終了する**。
4. 採用と判定した場合は Step A4 へ進む。

### Step A4: grilling で深掘りする

1. grilling スキル(`mattpocock-skills:grilling`)を呼び出す。
2. 深掘りの目的として、次の 2 点を言語化することを grilling 側に渡す。
   - なぜ書くのか(ゴール)
   - 書き手固有の切り口
3. grilling の対話が終わったら Step A5 へ進む。

### Step A5: neta Issue を作成する

1. 記録先リポジトリを特定する。

   ```bash
   gh repo view --json nameWithOwner -q .nameWithOwner
   ```

2. `neta` ラベルの有無を確認し、存在しなければ作成する。

   ```bash
   gh label list --search neta
   gh label create neta --description "ブログのネタ候補" --color "0e8a16"
   ```

3. `assets/neta-issue-template.md` を読み、その形式に厳密に従って本文を組み立てる。熱量メモにはユーザーの発言をそのまま引用する。
4. タイトルは「素材の主題 + 切り口」を 40 文字以内で書く。素材のページタイトルをそのまま流用しない。
5. Issue を作成する。

   ```bash
   gh issue create --title "<タイトル>" --label neta --body-file - <<'EOF'
   <組み立てた本文>
   EOF
   ```

6. 作成された Issue の URL をユーザーに伝える。

---

## モード B: ネタ選択

### Step B1: 記録済みネタを提示する

1. open な `neta` Issue を取得する。

   ```bash
   gh issue list --label neta --state open --json number,title,body --limit 30
   ```

2. 取得結果から 2〜3 件を選ぶ。選定は次の順で優先する。
   - 直近に作成されたもの
   - 検証すること が具体的に書かれているもの
3. 選んだ Issue を、番号・タイトル・ゴール 1 行・熱量メモの引用 1 行で提示する。全件を列挙しない。
4. どれを書くかをユーザーに選ばせ、ターンを終える。

### Step B2: blog-thinking へ引き継ぐ

1. 選ばれた Issue の本文を渡して blog-thinking へ切り替える。
2. Issue に記録済みの記事メッセージ・想定読者・切り口は、既に語られた内容として blog-thinking 側の制約条件になることを伝える。
3. 記事化して PR がマージされる際に、PR 本文へ `Closes #<番号>` を書けば Issue が自動で閉じることを伝える。

## Error Handling

- 作業ディレクトリが GitHub リポジトリでない、または `gh repo view` が失敗する場合は、Issue を作らずに記録先リポジトリを 1 問で確認し、`--repo <owner/name>` を付けて再実行する。
- `gh` が未認証の場合は、`gh auth login` の実行をユーザーに求め、その時点で作業を止める。組み立てた Issue 本文はチャットに残し、再実行時に使えるようにする。
- grilling スキルが利用できない場合は、Issue 作成へ進まず、grilling プラグインが未インストールであることを伝えて作業を止める。深掘りのロジックをこのスキル内で代替実装しない。
- 深掘りを経てもゴールか切り口のどちらかが言語化できない場合は、採用判定を取り消して見送り扱いにする。空欄を含む Issue を作らない。
- open な `neta` Issue が 0 件の場合は、モード B を続行せず、素材か作業ログを渡してモード A から始めるよう伝える。
- 入力が素材でも作業ログでもなく、既にテーマが定まった相談である場合は、このスキルを続行せず blog-thinking へ切り替える。
