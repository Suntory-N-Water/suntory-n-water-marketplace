# 調査と検証の方針

## 一次情報の調べ方

仕様、公式ドキュメント、公式のリポジトリ、リリースノート、Issue と Pull Request を優先します。検索結果の要約ではなく、元の資料を開きます。

分かったことは、驚いた制約や過去からの変更も含めてユーザーへ説明します。根拠が見つからない場合は、根拠を確認できなかったと書きます。

## 検証が必須になる型

型 1（変更への追随）、型 2（手を動かす解説）、型 3（調査と比較）では検証が必須です。型 4（意見と経験）では任意です。

環境が用意できず確かめられない場合は、その主張を未検証と明示し、記事を下書きのまま残します。確かめた結果として書けるのは、実際に動かして確認した結果だけです。

## 作業場所

`sui-blog/examples/<slug>/` に検証用のプロジェクトを作ります。ディレクトリが無ければ、記事のコードを動かす最小限の構成を新しく作ります。このディレクトリは `.gitignore` に入れ、Git では管理しません。

Git で管理しない理由は 2 つあります。記事を更新するときには対象のバージョンが変わっているため、古い検証用プロジェクトはそのまま使えず作り直しになります。また Renovate による依存関係の自動更新と CI の対象に入り、記事とは関係のない作業が発生します。

残す価値があるのはプロジェクトそのものではなく記録です。検証前に `verification.md` または日付付きの検証記録を作り、主張、確認する方法、成功と判断する条件を書きます。検証後に日付、環境、条件、確認した結果、確かめられなかったことを追記します。workflow、実行 ID、ログの該当部分も同じディレクトリに保存します。認証情報や秘密の値は保存しません。

## 検証の進め方

コードを書く前に、主張と、それをどう確認すれば確かめたことになるかを対にして検証記録へ書き出します。書き手が確かめた条件と、レビュー側が検証した条件は別々に記録します。条件が違う結果を比較する場合は、違いを明示し、書き手が確かめた結果を反証したとは扱いません。

| 主張の種類 | それを確かめる方法 |
|---|---|
| ある値を返す | 出力、アサーション |
| 失敗が起きる | 正確なエラーメッセージと、その発生条件 |
| 代替の動作が働く | 未対応の状態を再現したうえで確認した結果 |
| 選択肢 A と B が違う | 同じ入力を与えたときの、それぞれの出力 |
| 処理にかかる時間が変わる | 同じ条件での実行時間の記録 |

検証は、主張を支えるのに必要な範囲だけ行います。

検証用プロジェクトの作り方です。

- 対象の技術そのものを動かす
- UI やスタイルは、挙動を確認できる最小限にとどめる
- 依存パッケージ、import、設定ファイル、環境変数の名前まで書く
- 認証情報には、ダミーの値かその場限りのテスト用の値を使う
- Markdown の中のコード片を取り出すのではなく、プロジェクトとして通しで動かす
- 記事に示すコードは、検証したソースと一致させる

## 記録する項目

対象ごとに記録する項目が変わります。下の表は一例です。ここに載っていない対象を扱う場合は、同じ考え方（日付、環境、条件、確認した結果が後から追えること）で項目を決めます。

| 対象 | 記録する項目 |
|---|---|
| 共通 | 検証した日付、成功と判断する条件、実際に確認した結果、確かめられなかったこと。書き手が確かめたものかレビュー側が確かめたものか |
| ローカルで動くもの | OS、ランタイムとパッケージのバージョン、実行したコマンド |
| GitHub Actions | workflow、実行の URL または run ID、実行日時、ランナーの種類、所要時間、ログの該当部分 |
| Cloudflare Workers | デプロイのバージョン ID、実行した環境 |
| Claude Code | バージョン、モデル名 |

## 手元で動かせない対象の検証

GitHub Actions のように手元のマシンで完結しない対象は、使い捨てのリポジトリを作って動かします。

手順は次のとおりです。

1. `examples/<slug>/` を作り、そこにワークフローと検証記録を用意する
2. **実行前にユーザーへ承認を求める**
3. `gh repo create <名前> --private` で使い捨てのリポジトリを作る
4. push して実行する
5. `gh run view --log` で実行のログを取得する
6. workflow、実行の URL または run ID、実行日時、ランナーの種類、所要時間、ログの該当部分を `examples/<slug>/` の検証記録に保存する
7. 検証が成功したかにかかわらず、検証のために自分が作った使い捨てリポジトリを `gh repo delete <名前>` で削除する
8. 削除できたことを確認する。削除に失敗した場合は、残っているリポジトリと失敗理由を報告する

リポジトリの作成と削除は取り消しにくい操作のため、手順 2 の承認を必ず取ります。

実行のログ、本番環境で確認した結果、自分のリポジトリでの適用前後の測定値も、検証の証拠として扱います。形式は同じ（日付、環境、条件、確認した結果）です。

## 記事本文と検証用ディレクトリの関係

`examples/<slug>/` は書き手が確かめるための作業場所であり、読者の手元には渡りません。そのため記事本文には、読者が自分の環境だけで再現できる情報を書きます。ローカルのパス、ディレクトリ名、そこでの起動コマンド、リポジトリの場所は、記事の外に置きます。

記録には残すが記事には書かないものが 4 つあります。検証に使った環境とバージョンの一覧、確かめられなかったことの一覧、検証の計画と最初に立てた想定、自分の端末だけで起きたトラブルです。どれも書き手が作業を追えるようにするための記録であって、読者が必要とする情報ではありません。書き手が必要だと判断して指示した場合だけ記事に入れます。判断の基準は `sui-style.md` の「読者が知らないこと」にあります。

検証で得た情報そのものは記事に残します。確かめた条件と結果を、そのまま本文に書きます。

- 改善前: 「検証用サンプルでは 40 秒でした」
- 改善後: 「キャッシュを無効にした状態で実行したところ、40 秒でした」
