# sui-blog の記事を書く

記事は contents/blog/<YYYY-MM-DD>_<slug>.md に作成します。読者が自身の環境だけで再現できる形で、確かめた事実だけを書きます。

## 読み込む参照ファイル

| ファイル | 読むタイミング |
|---|---|
| references/sui-style.md | 合意確認の前、執筆の前、初稿作成前の点検、最終確認 |
| references/article-types.md | 構成を提案する前 |
| references/research-and-validation.md | 外部から確認可能な主張やコードを含む場合 |

文章や構成の規範は参照ファイルに定めています。この SKILL.md には執筆の手順を記載します。

## 手順

### 1. 依頼内容の把握

提示された素材や作業場所の情報を確認します。references/article-types.md を読み、4 つの型のいずれかに分類します。確認事項がある場合のみ、焦点を絞って質問します。

### 2. 第 1 回合意確認

references/sui-style.md を確認した上で進めます。次の項目について、推奨案とその理由を添えて確認します。

- 想定読者と、前提とする知識水準
- 読者が知らない語と、記事内で解説する語（独自ツール名、専門用語、仕様用語など）
- 読者が得られる結論、または実現できるようになること
- 記事で扱う範囲と、扱わない範囲
- 調査が必要な主張
- 実際に動かして検証すべき主張
- 検証環境と、検証成功の判定基準
- 記事の型と、見出し構成案
- タイトル案、概要説明（description）の方向性、URL 等に用いる識別名（slug）

決定事項、前提条件、採用しなかった選択肢、残っている検討事項を整理して提示し、利用者の承認を得ます。記事ファイルの作成は承認後に行います。

### 3. 一次情報の調査

references/research-and-validation.md の「一次情報の調べ方」に従います。仕様書、公式ドキュメント、公式リポジトリ、リリースノート、Issue や Pull Request を確認し、要約ではなく元の一次資料にあたります。判明した事実や制約を整理します。根拠が確認できなかった主張は、根拠未確認であることを明記します。

### 4. 実行による検証

references/research-and-validation.md に従い、作業用の検証ディレクトリ（examples/<slug>/ など）で実際に動かして確認します。実行前に、主張と検証方法を検証記録（verification.md など）に書き出し、日付、環境、条件、成功判定基準を記録します。実行ログ等も同ディレクトリに保存し、認証情報は記録しません。手元で動かせない対象で一時的なリポジトリを作成する場合は、事前に承認を得て、検証終了後に削除します。

### 5. 第 2 回合意確認

中心となる主張、集めた証拠、制約と互換性、見出し構成、検証結果、参照した一次資料を提示し、承認を得ます。内容が簡潔な記事の場合は、利用者の判断でこの確認を省略できます。

### 6. 執筆

references/sui-style.md を確認した上で、contents/blog/<YYYY-MM-DD>_<slug>.md を作成します。先頭の付加情報（frontmatter）は次の項目を設定します。

```yaml
title:
slug:
date: YYYY-MM-DD
modified_time: YYYY-MM-DD
description:
icon:
icon_url:
tags:
  -
```

description は単なる要約ではなく、背景、行ったこと、扱う範囲を 1〜3 文で記述します。一覧や検索結果だけで内容が把握できるようにします。本文と同様の敬体（です・ます調）で書き、文末は述語で終えます。

本文には、読者が自身の環境で再現できる情報のみを書きます。検証用ディレクトリは作業場所であり、読者には渡りません。ローカルパスや検証用ディレクトリ名、検証用リポジトリの場所は記事本文に含めず、確かめた条件と結果のみを記述します。

- 改善前: 「検証用サンプルでは 40 秒でした」
- 改善後: 「キャッシュを無効にした状態で実行したところ、40 秒でした」

references/sui-style.md の「読者が知らないこと」に沿って記述します。検証の試行錯誤、当初の想定、手元固有のトラブルなどは記事本文には含めず、検証記録側に残します。

### 7. 初稿完成前の点検

執筆完了後、利用者に提示する前に以下の項目を点検します。

1. 校正ツールの指摘の解消: 指摘された語句の表面的な置換にとどまらず、動作や状況が正確に伝わる記述に直します。
2. 執筆過程の混入確認: 「読者が知らないこと」の項目に照らし、説明のない初出語、「前回」などの相対参照、未検証事項の単なる列挙、環境一覧が本文に残っていないか確認します。
3. まとめ節の確認: ## まとめ が本文の結論を再掲した箇条書きのみになっているか、本文の最後の節が書き手自身の判断で締められているかを確認します。
4. 見出しの確認: 比喩的な表現や内容が不明瞭な表現がないか確認します。
5. 表の確認: 読者が注目すべき行が明確に示されているかを確認します。

### 8. 推敲と技術確認

article-review と tech-review の観点で確認を行います。利用できない環境では references/sui-style.md に照らして自身で確認します。日本語と英数字の間の半角スペースなど、自動確認の対象外の項目も手動で確認します。

### 9. 報告

次の項目を整理して利用者に報告します。

- 記事のファイルパス
- 記事の型
- 想定読者
- 中心となる主張
- 参照した一次情報
- 検証記録（日付、環境、実行コマンド、結果）
- 実施できなかった確認事項
- 残存タスク

公開、翻訳、コミット、push は、指示があった場合のみ行います。

## 判断に迷ったとき

- 型が複数にまたがる場合は、中心となる根拠の種類で判断します。動作検証結果が中心なら型 1 または型 2、集計データが中心なら型 3、書き手の判断が中心なら型 4 を選択します。
- 検証環境が用意できない主張は未検証であることを明記し、下書きの段階にとどめます。
- 素材の段階で記事化できるか判断がつかない場合は、pick-blog-topic へ切り替えます。
