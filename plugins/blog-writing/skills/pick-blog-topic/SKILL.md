# ブログの題材を判定する

記事の切り口と、主張を支える材料が揃っているかを判定する。結果は「今すぐ書く」「材料が足りない」「見送る」のいずれかとする。材料が足りない題材は、本番サイトの EmDash にある `ideas` コレクションに記録し、あとで選び直せるようにする。

## 前提

- 作業フォルダの `.mcp.json` に、本番サイトの MCP サーバー `emdash-site` が登録され、ログイン済みである
- 本番サイトに `ideas` コレクションがある。`schema_get_collection` に `ideas` を渡して確かめる。見つからない場合は記録と選択を行わず、登録用の内容を会話で示して、コレクションの作成を利用者に依頼する

## `ideas` コレクション

公開ページを持たない、題材の記録専用のコレクションである。エントリーは常に下書きのまま扱い、公開しない。公開しても表示するページがなく、下書きであれば公開用の API からも読まれないためである。

| フィールド | 型 | 内容 |
|---|---|---|
| `title` | string | 題材と記事の切り口が分かる 40 文字以内の日本語 |
| `question` | text | 記事で答える問いを 1〜2 文で書く |
| `stage` | select | 題材の状態。値は下表のとおり |
| `body` | portableText | 参照資料、会話で整理した内容、具体例、足りないもの、確かめること。形式は [本文の形式](assets/idea-entry-template.md) に従う |

| `stage` の値 | 意味 |
|---|---|
| `未着手` | まだ記事にしていない |
| `完了` | 記事にした |
| `ボツ` | 記事にしないと決めた |

- [入力の読み取り、質問、判定](references/topic-questions.md): 入力から拾う情報、質問の作り方、判定の条件を確認するときに読む
- [本文の形式](assets/idea-entry-template.md): `body` に書く内容を組み立てるときに読む

## 進め方

### 1. 入力と会話履歴を確認する

入力を「素材」「作業記録」「会話」「記録済みの題材一覧」に分ける。分類方法と各入力から拾う情報は、[入力の読み取り、質問、判定](references/topic-questions.md) を参照する。「次に何を書くか決めたい」という依頼は「記録済みの題材から選ぶ」へ進む。

会話が入力に含まれる場合は、記事の問い、会話で整理された説明、役立つ例やコード、利用者が述べた経験や見方、未確認の点を拾う。抜粋だけでは話題の意味や出所を判断できないときは、取得できる関連部分を追加で確認する。

記録する情報は、出所と確認状況を区別する。たとえば、利用者の経験、会話中に AI が示した説明例、資料で確認した事実、実際に試した結果を別々に扱う。AI が示した数値やコードは、資料や実行結果で確かめたかどうかが分かるように記載する。

会話中の言い回しは、記事の問いや主張を伝えるうえで原文が役立つ場合に引用する。それ以外は、記事に関係する要点としてまとめる。

### 2. 同じ切り口の記事と題材を探す

判定の前に、同じ切り口がすでにあるかを確かめる。

- 公開記事: `search` を `collections: ["posts"]` で呼び、題材の固有名詞や主題で検索する
- 記録済みの題材: `content_list` を `collection: "ideas"`、`limit: 100` で呼び、全件の `title` と `question` を読んで比べる。`search` が下書きを検索対象に含めるかは確認していないため、題材の重複確認には使わない

見つかった記事や題材は、その内容と `stage` を判定に使う。

### 3. 必要な質問をする

会話履歴と提供資料から、回答済みの点を確認する。回答によって記事の切り口や判定が変わる未解決点がある場合に、具体的な質問を 1〜2 問する。質問を出したターンは質問だけで終え、回答を受けて判定を続ける。

### 4. 題材を判定する

判定条件は [入力の読み取り、質問、判定](references/topic-questions.md) に従う。

### 5. 判定と理由を伝える

- **今すぐ書く**: 記事の型、中心となる問い、揃っている根拠を簡潔に示し、`write-blog-article` へ引き継ぐ情報を整理する
- **材料が足りない**: 何が分かっていて何を確認する必要があるかを示す。利用者が記録を希望した場合は「題材を記録する」の手順で `ideas` に登録する
- **見送る**: 理由と不足している材料を伝える

## 題材を記録する

1. 手順 2 で同じ切り口の題材が見つかった場合は、その内容を示し、既存のエントリーを更新するか新しく作るかを利用者に確認する
2. [本文の形式](assets/idea-entry-template.md) に沿って `body` を Markdown で組み立てる。記事の問い、説明、具体例、出所、確認状況、残っている調査や検証だけを記録する
3. `content_create` を次の引数で呼ぶ。`status` は渡さない。渡さなければ下書きになる
   - `collection`: `"ideas"`
   - `data`: `title`、`question`、`stage: "未着手"`、`body`
4. `content_get` で登録内容を読み返し、`title`、`question`、`stage`、`body` が意図どおりかを確かめる
5. 登録したエントリーの id と `title` を伝える。管理画面では `https://suntory-n-water.com/_emdash/admin` の「記事の題材」から開ける

既存のエントリーを更新する場合は、`content_get` で `_rev` を取得し、`content_update` に `id`、`_rev`、変更するフィールドだけを渡す。

MCP で登録できない場合は、組み立てた `title`、`question`、`body` を会話で示す。

## 記録済みの題材から選ぶ

1. `content_list` を `collection: "ideas"`、`limit: 100` で呼び、`stage` が `未着手` のエントリーを取り出す
2. 記事に進みやすい 2〜3 件を示す。更新日が新しいものと、「確かめること」が具体的に書かれているものを優先する。各候補には id、`title`、`question`、足りない材料を 1 行ずつ添え、全件は並べない
3. 利用者に選んでもらい、ターンを終える
4. 選ばれたエントリーを `content_get` で読み、`body` の「足りないもの」と「確かめること」を、`write-blog-article` の最初の合意確認で扱う調査と検証の項目として引き継ぐ

`未着手` のエントリーがない場合は、その旨を伝え、新しい素材や作業記録を受け取って手順 1 から始める。

## 題材の状態を変える

題材から書いた記事が `posts` に登録されたら、`content_update` で `stage` を `完了` にする。記事にしないと決めた題材は `stage` を `ボツ` にし、理由を `body` の末尾に追記する。エントリーは削除しない。
