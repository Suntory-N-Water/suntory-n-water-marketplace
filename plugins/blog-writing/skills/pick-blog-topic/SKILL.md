# ブログの題材を判定する

記事の切り口と、主張を支える材料が揃っているかを判定する。結果は「今すぐ書く」「材料が足りない」「見送る」のいずれかとする。

## 参照資料

- [入力の読み取り、質問、判定](references/topic-questions.md): 入力から拾う情報、必要な質問、判定の条件を確認するときに読む。
- [Issue本文の形式](assets/neta-issue-template.md): 材料が足りない題材を Issue に登録するときに読む。

## 進め方

### 1. 入力と会話履歴を確認する

入力を「素材」「作業記録」「会話」「既存のネタ一覧」に分ける。分類方法と各入力から拾う情報は、[入力の読み取り、質問、判定](references/topic-questions.md)を参照する。

会話が入力に含まれる場合は、記事の問い、会話で整理された説明、役立つ例やコード、ユーザーが述べた経験や見方、未確認の点を拾う。抜粋だけでは話題の意味や出所を判断できないときは、取得できる関連部分を追加で確認する。

記録する情報は、出所と確認状況を区別する。たとえば、ユーザーの経験、会話中に AI が示した説明例、資料で確認した事実、実際に試した結果を別々に扱う。AI が示した数値やコードは、資料や実行結果で確かめた状態が分かるように記載する。

会話中の言い回しは、記事の問いや主張を伝えるうえで原文が役立つ場合に引用する。それ以外は、記事に関係する要点としてまとめる。Issue本文は、題材、記事の問い、説明、具体例、検証に必要な情報で構成する。

### 2. 必要な質問をする

会話履歴と提供資料から回答済みの点を確認する。回答によって記事の切り口や判定が変わる未解決点がある場合に、具体的な質問を 1〜2 問する。質問を出したターンは質問だけで終え、回答を受けて判定を続ける。

### 3. 題材を判定する

判定条件は[入力の読み取り、質問、判定](references/topic-questions.md)に従う。同じ切り口の既存記事やネタがある場合は、その状態と内容を確認してから判定する。

### 4. 判定と理由を伝える

- **今すぐ書く**: 記事の型、中心となる問い、揃っている根拠を簡潔に示し、`write-blog-article` へ引き継ぐ情報を整理する。
- **材料が足りない**: 何が分かっていて何を確認する必要があるかを示す。ユーザーがネタの登録を依頼した場合は、次の手順で GitHub Issue を作成する。
- **見送る**: 理由と不足している材料を伝える。

## ネタを GitHub Issue に登録する

1. ユーザーが指定した登録先を確認する。指定がない場合は作業フォルダからリポジトリを特定する。登録先を特定できない場合や、提示された URL の役割を判断できない場合は、登録先を質問する。
2. 登録先に同じ題材の `neta` Issue があるか、未完了と完了の両方から調べる。関連 Issue が見つかった場合は内容を示し、既存 Issue の更新や再開が必要か確認する。
3. `neta` ラベルの有無を確認する。ラベルがない場合は「ブログのネタ候補」という説明と `0e8a16` の色で作成する。
4. [Issue本文の形式](assets/neta-issue-template.md)に沿って、記事の問い、説明、具体例、出所、確認状況、残っている調査や検証だけを記録する。
5. タイトルは、題材と記事の切り口が分かる 40 文字以内の日本語にする。
6. `neta` ラベルを付けて Issue を作成し、タイトル、本文、ラベルを読み返してから URL を伝える。

GitHub への登録ができない場合は、登録用の本文と登録先を会話で示す。

Issue を作成するコマンドの例:

```bash
gh issue create --repo <owner/name> --title "<タイトル>" --label neta --body-file - <<'EOF'
<組み立てた本文>
EOF
```

## 既存のネタから選ぶ

未完了の `neta` Issue を取得し、記事に進みやすい 2〜3 件を示す。各候補には番号、タイトル、記事の切り口、足りない材料を添える。ユーザーが選んだ Issue の内容を、`write-blog-article` に引き継ぐために整理する。

未完了の Issue が見つからない場合は、その旨を伝え、新しい題材や素材を受け取る。
