# ブログのネタを判定する

素材や作業の記録を読み、記事を書くだけの根拠になる情報があるかを判定します。詳細な構成や検証項目の検討は write-blog-article の合意確認で行うため、ここでは切り口の有無と根拠となる情報の揃い方を確認します。

## 前提

- 利用者との対話を行うスキルです。質問を出力したターンはそこで停止し、利用者の回答を待ちます。
- 他のプラグインのスキルを直接呼び出さずに単独で動作します。
- GitHub の課題（Issue）を作成するのは「材料が足りない」と判定したときだけです。「今すぐ書く」は write-blog-article へ引き継ぎ、「見送る」は理由のみを伝えます。
- 使うラベルは neta の 1 種類です。状態は未完了（open）または完了（closed）の 2 値で管理します。
- 記録先は、このスキルを呼び出した作業ディレクトリの GitHub リポジトリとします。

## 参照ファイル

- references/topic-questions.md: 入力の種類の判定、質問の作成方法、3 つの判定基準。手順 1 の前に読みます。
- assets/neta-issue-template.md: Issue 本文の形式。Issue を作成する直前に読みます。

## 手順

### 1. 入力の種類を判定する

references/topic-questions.md を読み、入力を次の 3 つのいずれかに分類します。

| 入力 | 特徴 | 次の手順 |
|---|---|---|
| 素材 | URL とページ本文、記事やドキュメントの引用 | 手順 2 へ |
| 作業の記録 | 実際に手を動かしたときのメモ。コマンド、エラー、詰まった箇所、所感 | 手順 2 へ |
| 記録済みの Issue の一覧 | 「次のネタを選びたい」「何を書くか決めたい」という依頼 | 「Issue から選ぶ」へ |

分類の結果を利用者に 1 行で伝えます。

### 2. 具体的な質問を 1〜2 問行う

素材の固有名詞や数値に結びつけた質問を作成します（例: 「7 分かかっていたのは pnpm のインストールですか、依存関係の解決ですか」）。質問の作成方法は references/topic-questions.md に従います。質問を出力してターンを終了し、回答を待ちます。

### 3. 判定する

回答を references/topic-questions.md の基準に照らし、3 つの分類から 1 つを決定します。

| 結果 | 条件 | 次の動作 |
|---|---|---|
| 今すぐ書く | 記事の型が決まり、主張を支える根拠（動かせるコード、測定データ、一次情報）が揃っている | write-blog-article へ引き継ぐ |
| 材料が足りない | 切り口はあるが、検証や調査が未完了である | neta ラベル付きの Issue に記録する |
| 見送る | すでに書かれている、切り口が見つからず根拠も不足している、記事にする理由がない | 理由のみを伝える |

判断に迷う場合は、具体的な質問をもう 1 問だけ行って再判定します。

### 4. 判定の理由を伝える

判定結果と、どの根拠が揃っていて何が不足しているかを伝えます。

- 今すぐ書く: 記事の型、切り口、揃っている根拠を 3 行で示し、write-blog-article へ切り替えます。素材と回答は、最初の合意確認で使う入力として渡します。
- 材料が足りない: Issue を作成し、URL を伝えます（後述の「Issue に記録する」に従います）。
- 見送る: 見送りと判断した旨と、どの根拠が不足していたかの 2 点を伝えます。素材の URL は対話の本文に残します。

## Issue に記録する

1. 記録先のリポジトリを特定します。

   ```bash
   gh repo view --json nameWithOwner -q .nameWithOwner
   ```

2. neta ラベルが無ければ作成します。

   ```bash
   gh label list --search neta
   gh label create neta --description "ブログのネタ候補" --color "0e8a16"
   ```

3. assets/neta-issue-template.md を読み、その形式で本文を組み立てます。利用者の発言は、そのままの言葉で引用し、要約や言い換えを行いません。
4. タイトルは「素材の主題 + 切り口」を 40 文字以内で作成します。素材のページタイトルをそのまま流用しません。
5. Issue を作成します。

   ```bash
   gh issue create --title "<タイトル>" --label neta --body-file - <<'EOF'
   <組み立てた本文>
   EOF
   ```

6. 作成した Issue の URL を利用者に伝えます。

## Issue から選ぶ

1. 未完了（open）の neta Issue を取得します。

   ```bash
   gh issue list --label neta --state open --json number,title,body --limit 30
   ```

2. 2〜3 件を選んで提示します。直近に作成されたものや、「確かめる必要があること」が具体的に記載されているものを優先します。番号、タイトル、不足している情報 1 行、引用 1 行で示し、全件の列挙は避けます。
3. どれを書くかを利用者に選んでもらい、ターンを終了します。
4. 選択された Issue の本文を渡して write-blog-article へ切り替えます。Issue に記載された「足りないもの」と「確かめる必要があること」は、最初の合意確認における調査・検証の項目になります。

## 想定される例外対応

- 作業ディレクトリが GitHub リポジトリでない、または gh repo view が失敗する場合は、記録先を確認し、--repo <owner/name> を指定して実行します。
- gh コマンドが未認証の場合は、gh auth login の実行を利用者に案内して処理を停止します。組み立てた Issue 本文は対話ログに残し、再開時に使えるようにします。
- 未完了の neta Issue が 0 件の場合は、素材または作業記録の提示を促し、手順 1 から開始します。
- 入力が素材や作業記録ではなく、すでにテーマが確定した執筆依頼である場合は、write-blog-article へ切り替えます。
