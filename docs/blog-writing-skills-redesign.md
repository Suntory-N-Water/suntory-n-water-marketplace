# blog-writing-skills 再設計仕様

## この文書について

`plugins/blog-writing-skills/` を作り直すための仕様書です。実装者はこの文書だけを読んで作業できます。

対象のブログは https://github.com/Suntory-N-Water/sui-blog です。記事は `contents/blog/<YYYY-MM-DD>_<slug>.md` に置かれ、Astro でビルドされます。

## 目的

ブログ記事を書く一連の作業を、5 つのスキルに分けて定義します。

現在のプラグインには 7 つのスキルがありますが、執筆の工程で分割されているため、工程をまたいで適用される規則（文体、結論を置く位置）が複数のスキルに分散しています。その結果、指示の食い違いが発生しています。たとえば「冒頭で結論を出す」と「ここですぐに解決策を提示しない」が別々のスキルに書かれ、どちらに従うかの判断ができません。また同じ規則が SKILL.md と references の両方に同じ文章のまま置かれています。

再設計では、分割の軸を工程から役割へ変更し、文章の規範を 1 ファイルに集約します。

## 全体の構成

5 つのスキルを作ります。

| スキル名 | 役割 | 主な成果物 |
|---|---|---|
| `pick-blog-topic` | 溜めた素材や作業の記録から、記事にできるかを判定する | 判定の結果。書ける場合は執筆スキルへ渡す材料 |
| `write-blog-article` | 一次情報を調べ、動かして確かめ、記事の初稿を書く | `contents/blog/<YYYY-MM-DD>_<slug>.md` |
| `article-review` | 構成と日本語を読み、指摘を返す | 指摘の一覧 |
| `tech-review` | 技術的な正しさ、証拠、再現できるかを確かめる | 指摘の一覧 |
| `japanese-sentence-order` | 一文の中の語順と読点だけを見る | 指摘の一覧 |

作業の流れは `pick-blog-topic` → `write-blog-article` → `article-review` / `tech-review` です。`japanese-sentence-order` はブログ以外の日本語の文章にも使うため、どこからでも単独で起動できます。

### 役割で分ける理由

編集の観点（構成、日本語、読者が追えるか）と技術の観点（一次情報の裏取り、コードが動くか、バージョンの記載）を同時に見ると、片方が雑になります。そのため `article-review` と `tech-review` を分けます。

`pick-blog-topic` を執筆スキルに含めない理由は、起動する場面が違うためです。ネタの判定は記事を書き始める前ではなく、素材が溜まった時点や作業を終えた時点で行います。

### 廃止するスキル

既存の 7 スキルはすべて無くします。ただし内容を引き写す元として使うため、作業中は一時ディレクトリへ移し、5 つのスキルを作り終えてから削除します。

| 廃止するスキル | 扱い |
|---|---|
| `blog-triage` | `pick-blog-topic` として作り直す。判定の結果を 3 つにする（後述） |
| `blog-thinking` | 削除。役割は `write-blog-article` の 1 回目の合意確認に含める |
| `blog-structuring` | 削除。役割は `write-blog-article` の 1 回目の合意確認に含める |
| `blog-drafting` | `write-blog-article` として作り直す |
| `blog-revision` | `article-review` として作り直す |
| `japanese-tech-writing` | 削除。内容の一部を `write-blog-article/references/sui-style.md` と `article-review` に移す |
| `cognitive-rhythm-writing` | 削除。内容の一部を `article-review` に移す |

プラグイン名 `blog-writing-skills` は変更しません。sui-blog 側の `skills-lock.json` とインストール設定を書き換えずに済ませるためです。

## 記事の型

記事を 4 つの型に分けます。型ごとに、導入の書き方、見出しの進行、検証の要否が変わります。

型を 4 つに保ちます。5 つ以上になると、書き始めるときにどれを選ぶかで迷います。

### 型 1: 変更への追随

対象は、ツールやサービスの仕様が変わり、従来のやり方が使えなくなった、または推奨されなくなった場合です。sui-blog で最も多い型です。

見出しの進行:

1. 従来は定番だったやり方
2. 変わった事情（CHANGELOG、Issue、Pull Request、公式のアナウンスを根拠にする）
3. 新しいやり方
4. 実際に動かした結果
5. 移行するときに確認する制約
6. まとめ
7. 参考

導入は、技術的な背景から入ります。読者が今も使っているであろう従来のやり方を最初に置き、そこから変更の話に進みます。

一次情報として読む対象は、対象ツールの CHANGELOG、リリースノート、GitHub の Issue と Pull Request、公式ドキュメントです。

検証は必須です。

### 型 2: 手を動かす解説

対象は、読者が同じものを作れるようにする記事、および自分が作ったものを紹介する記事です。

見出しの進行:

1. 何を作るか、完成した状態
2. 構成の図（説明の助けになる場合）
3. 前提、インストール、初期設定
4. ファイル単位で段階的に実装する
5. 起動と操作のコマンド
6. 期待する出力と、実際に観測した結果
7. 運用上の注意、応用
8. まとめ
9. 参考

導入は、技術的な背景から入ります。

初めての環境で再現できる形にします。import、環境変数、設定、起動の手順まで書きます。

検証は必須です。

### 型 3: 調査と比較

対象は、選択肢を比べる記事、実測した値を示す記事です。

見出しの進行:

1. 何を判断したいのか
2. 調査の範囲、評価の基準、検証した環境
3. 判断に必要な前提知識
4. 選択肢ごとの観測結果（同じ条件で測る）
5. 共通点と違い
6. 調査の結果から導いた判断の基準
7. まとめ
8. 参考

導入は、技術的な背景から入ります。

この型では、自分で取ったデータの集計表が説明の中心になります。集計の条件（対象、期間、件数、除外したもの）を必ず書きます。

検証は必須です。

### 型 4: 意見と経験

対象は、技術についての意見、旅行や生活の記録、健康データの分析です。

見出しの進行:

1. 今の立場と、そこに至るまでの変化
2. 話題ごとの実践とその理由
3. 利点だけでなく、限界と反論
4. どこまでが一般化できるか
5. 今後変わりそうな点
6. まとめ
7. 参考（外部の資料を使った場合）

導入は 2 通りです。個人の体験を一文で置く形（「2025 年 8 月、二度目の父島へ行ってきました。」）か、読者への呼びかけから入る形（「Claude Code、長く話していると最初に出した指示を無視されはじめますよね。」）です。

一人称を使います。個人の経験は、自分が経験したこととして書きます。

コードを動かす検証は任意です。数値を挙げる場合は、その出所と集計の条件を書きます。

## 文章の規範

規範の本体はこのマーケットプレイスのリポジトリ側、`plugins/blog-writing-skills/skills/write-blog-article/references/sui-style.md` に置きます。sui-blog のリポジトリには置きません。sui-blog 側に置くとスキルが別のリポジトリのファイルを読むことになり、プラグインだけを入れた環境で規範が欠けるためです。

`article-review` と `tech-review` は、同じプラグインの中の相対パス（`../../write-blog-article/references/sui-style.md`）でこのファイルを読みます。同じ規則を複数のファイルに書きません。

正規表現による自動検査（`~/.claude/scripts/typescript/style-rules/rules.ts`）と textlint は、この規範の一部を自動化したものとして扱います。規範の側には「この項目は自動検査がある」と書き添えるだけにし、規範を自動検査に合わせて書き換えません。

### 既存スキルからの引き写し方

この節の以降の内容には、既存スキルの本文をそのまま持ってくる部分があります。該当する部分は、下の表に示した元のファイルと節を開き、**本文と例をそのまま引き写します**。この仕様書に書かれた説明は、どの節を持ってくるかを指すためのものであり、要約ではありません。要約したり言い換えたりすると、元の規範が持っている判断の基準と例が失われます。

| この仕様書の節 | 引き写す元 |
|---|---|
| 使わない言い回し | `japanese-tech-writing/references/norms.md` の「LLM っぽい表現の禁止」「冗長の排除」「演出の抑制」 |
| 論証 | `japanese-tech-writing/references/norms.md` の「論証の厳密さ」 |
| 見出しの付け方 | `japanese-tech-writing/references/norms.md` の「見出しの付け方」 |
| 話題テスト | `cognitive-rhythm-writing/SKILL.md` の「緩みと駄文の見分け方」 |

引き写したあとに手を入れてよいのは次の 2 点だけです。

1. 常体（「〜である」）で書かれた例文を、敬体（「〜です」）に直す
2. 書籍の原稿を前提にした語（「本章」「本節」）を、記事を前提にした語（「この記事」「この節」）に直す

判断の基準そのもの、例の数、例外の扱いは、元のまま維持します。

### 数値の目安

数値は、初稿が薄いかどうかを判断する材料です。目標値ではありません。

| 指標（中央値） | sui-blog の 2026 年 26 本 | azukiazusa 氏の 2025 年以降 163 本 |
|---|---:|---:|
| 本文の文字数 | 6,043 | 9,735 |
| `##` 見出しの数 | 7 | 6 |
| コードブロックの数 | 3.5 | 9 |

両方を併記します。見出しの数はほぼ同じで、文字数とコードブロックの数だけが 1.6 倍と 2.6 倍の差になっています。この差の形から、足すべきものが記事全体の分量ではなく、1 つの見出しの中身だと判断できます。

数値そのものより次の条件を優先します。

**見出し 1 つにつき、主張とその根拠が最低 1 組あること。** 根拠になるのは、動かしたコード、実行のログ、集計した表、一次情報からの引用です。

### 構成

すべての型に共通する部分です。

- 本文は導入の文章から始める。記事タイトルは frontmatter の `title` が表示されるため、本文の見出しは `##` から始める
- 本文の大きな区分は `##`、その内訳は `###` を使う
- `## まとめ` を置く。本文で述べた結論だけを、単独で読んでも意味が通る箇条書きにする
- `## 参考` を置く。一次情報へのリンクを並べる。本文中でも、根拠になる箇所から直接リンクする
- バージョンに依存する話、実験的な機能を扱う場合は、導入の直後に GitHub の警告ブロック記法（`> [!NOTE]` など）を置き、対象のバージョンと検証した日付を書く。種類は内容に合わせて選ぶ。前提の共有は `> [!NOTE]`、勧めたい手順は `> [!TIP]`、読み飛ばすと困ることは `> [!IMPORTANT]`、破壊的変更や失敗する条件は `> [!WARNING]`、取り返しがつかない操作は `> [!CAUTION]`

### 文体

規則として守るものです。

- 「です・ます」の敬体で統一する
- 一人称は「私」を使う
- 日本語と英数字の間に半角スペースを入れる（`GitHub Actions の`、`7 分`、`2026 年 9 月 4 日`）。句読点、かぎかっこ、丸かっこなどの記号は、そのまま続けて書く（`pnpm。`）
- 数字は半角を使う
- 連続する 3 文の文末は 2 種類以上にする（例: 「〜しました。」「〜になります。」「〜と考えています。」を混ぜる）
- 主語、目的語、述語の順で書く（例: 「この方法のほうが速いです。」）
- 文は述語で終える（例: 「原因はキャッシュの設定でした。」）
- 1 つの文に書くのは 1 つのことだけにする。原因、操作、結果はそれぞれ別の文に分ける
- 推測は「〜と考えられます」「〜可能性があります」と書き、確認した事実と区別する
- 強く断定する場合は、仕様、公式の文書、実行結果のいずれかを根拠にする
- 同じ概念は、最初に使った言い方で通す

再現したい書き方です。

- **脚注による用語の注釈**: 本文の流れを止めずに用語を説明する場合、脚注（`[^ラベル]`）に書く。2026 年の記事では 1 記事あたり 1 個程度使われている
- **譲歩してから反転する**: 反対の立場を一度そのまま認めてから、事実で反転させる（「これは合理的な判断です。間違っていません。」の直後に「それでも、実害はありませんでした。」）
- **`> [!NOTE]` による前提の明示**: 対象のバージョンや動作環境を、導入の近くに置く

観察された傾向として記録するだけで、規則にはしないものです。書かせる指示にすると、機械的に散りばめられて不自然になります。

- 「実際に」（2026 年の 26 本で 49 回）
- 「そのため」（12 回）、「つまり」（9 回）
- 「〜な気がします」「〜と思っています」といった柔らかい言い方

### 使わない言い回し

引き写す元: `japanese-tech-writing/references/norms.md` の「LLM っぽい表現の禁止」「冗長の排除」「演出の抑制」。下の表はその内容の見取り図です。実際の references には元の節の本文をそのまま置きます。

内容を足さずに、書けている感じだけを付ける言い方です。

| 種類 | 例 | 代わりに書くこと |
|---|---|---|
| 予告と総括 | 「重要なのは〜である」「本章では〜を扱う」「まとめると」「〜に他ならない」 | 主張をそのまま書く |
| 姿勢の宣言 | 「正面から扱う」「正面から回収する」 | 動作だけを書く |
| 中身のない形容 | 「核心的」「鍵となる」「根本的な」「多角的」「包括的」 | 何が無いと何ができなくなるかを書く |
| 中身のない動詞 | 「掘り下げる」「深掘りする」「言語化する」「触れる」 | 何をどう書いたかを示す |
| 情報を足さない接続 | 「〜において」「〜という側面から」「〜の観点から」、「さらに」「また」「加えて」の連打 | 削る |
| 根拠のない強調と緩和 | 「非常に」「極めて」「大いに」、根拠なく主張を弱める「〜と言えるだろう」 | 削る。推量、仮定、読者が抱く疑問を表す場合は残す |

この一覧は正規表現による自動検査にも入っています。

### 論証

引き写す元: `japanese-tech-writing/references/norms.md` の「論証の厳密さ」。下は含まれる項目の一覧です。

- 推量として書かれている文は、推量のまま残す。断定に直すのは、本文の中の根拠で確定している場合だけにする
- 区別すべき対象には、別々の言葉を当てる
- 複数の要因がある事象は、要因を並べて書く
- 原因を述べるときは、なぜそうなるのかを一文で添える
- 検出、保証、解決について書くときは、それが成り立つ条件を付ける
- 節をまたいで、同じ概念の扱いを揃える
- 挙げた例が主張の全体を支えているかを確かめる。例が一部だけを支える場合は、主張の範囲を例に合わせて狭める

### 見出しの付け方

引き写す元: `japanese-tech-writing/references/norms.md` の「見出しの付け方」。

- その節が答える問い、または扱う対象を指す句にする。結論は本文に置く
- 見出しには、その節で何が分かるのかを入れる
- 疑問形でも名詞句でもよい

### 話題テスト

引き写す元: `cognitive-rhythm-writing/SKILL.md` の「緩みと駄文の見分け方」。判定の軸と、例外として残してよい 4 つの形は、元の節に書かれた例文ごとそのまま持ってきます。

文を残すか削るかの判定です。軸は 1 つです。

**その文が新しく伝えるのは「対象そのもののこと」か、「この文章自体のこと」か。**

対象そのもののことを伝える文は残します。対象の性質、データ、観測した結果、書き手の判断の状態（思い込み、保留、後悔）が該当します。

この文章自体のことしか伝えない文は削ります。「ここまでだと概念の説明に見えるだろう」「次は〜を見る」「〜の列挙はしない」が該当します。短く断定の形に整えても、伝えている内容が文章自体のことなら削ります。

例外として残してよい形が 4 つあります。

1. 読者の誤読を「」で具体的に書き出して退ける文
2. 問いを立てる文と、その問いに答える文
3. 章や節の境界に置く、読者への断り
4. 例の枠を開く文（「〜としよう」）と閉じる文

### コードの扱い

- コピーして試せる単位で載せる
- 必要な import、インストール、起動のコマンドまで載せる
- 最小の例から始め、段階的に足す
- ファイルを作る場合は、コードブロックの言語指定にパスを付ける（` ```ts:src/example.ts `）
- 変更点の比較には `diff` を使う
- コードの中のコメントには、選んだ理由や注意点を書く
- コードの直後に、見るべき行と期待する結果を説明する
- バージョンに依存する場合は、インストールの例でバージョンを固定する

### 画像と動画

- 文章だけでは確認しにくい結果（画面、開発者ツール、ログ）に使う
- 画像の前に「何を見るのか」、後に「何が確認できたのか」を書く
- 動きや時間の変化が関係する場合は動画を使う
- 載せる画像は、実際に撮ったものだけにする。用意できない場合は、その位置に次のコメントを残す

```markdown
<!-- TODO(media): <スクリーンショット|動画> を入れる。<どの状態・操作> を写す。読者が観測するのは <具体的な結果>。代替テキスト: <説明> -->
```

コメントの前に何を見るのかを書き、後に期待する結果を書きます。

## 検証の方針

### 検証が必須になる型

型 1（変更への追随）、型 2（手を動かす解説）、型 3（調査と比較）では検証が必須です。型 4（意見と経験）では任意です。

環境が用意できず確かめられない場合は、その主張を未検証と明示し、記事を下書きのまま残します。観測した結果として書けるのは、実際に動かして見た結果だけです。

### 作業場所

`sui-blog/examples/<slug>/` に検証用のプロジェクトを作ります。このディレクトリは `.gitignore` に入れ、Git では管理しません。

Git で管理しない理由は 2 つあります。記事を更新するときには対象のバージョンが変わっているため、古い検証用プロジェクトはそのまま使えず作り直しになります。また Renovate による依存関係の自動更新と CI の対象に入り、記事とは関係のない作業が発生します。

残す価値があるのはプロジェクトそのものではなく記録です。記録は記事の中に書かれることで残ります。

### 検証の進め方

コードを書く前に、主張と、それをどう観測すれば確かめたことになるかを対にして書き出します。

| 主張の種類 | それを確かめる観測 |
|---|---|
| ある値を返す | 出力、アサーション |
| 失敗が起きる | 正確なエラーメッセージと、その発生条件 |
| 代替の動作が働く | 未対応の状態を再現したうえでの観測結果 |
| 選択肢 A と B が違う | 同じ入力を与えたときの、それぞれの出力 |
| 処理にかかる時間が変わる | 同じ条件での実行時間の記録 |

検証は、主張を支えるのに必要な範囲だけ行います。

検証用プロジェクトの作り方です。

- 対象の技術そのものを動かす
- UI やスタイルは、挙動を観測できる最小限にとどめる
- 依存パッケージ、import、設定ファイル、環境変数の名前まで書く
- 認証情報には、ダミーの値かその場限りのテスト用の値を使う
- Markdown の中のコード片を取り出すのではなく、プロジェクトとして通しで動かす
- 記事に載せるコードは、検証したソースと一致させる

### 記録する項目

対象ごとに記録する項目が変わります。下の表は一例です。ここに載っていない対象を扱う場合は、同じ考え方（日付、環境、条件、観測結果が後から追えること）で項目を決めます。

| 対象 | 記録する項目 |
|---|---|
| 共通 | 検証した日付、成功と判断する条件、実際に観測した結果、確かめられなかったこと |
| ローカルで動くもの | OS、ランタイムとパッケージのバージョン、実行したコマンド |
| GitHub Actions | 実行の URL、実行日時、ランナーの種類、所要時間 |
| Cloudflare Workers | デプロイのバージョン ID、実行した環境 |
| Claude Code | バージョン、モデル名 |

### 手元で動かせない対象の検証

GitHub Actions のように手元のマシンで完結しない対象は、使い捨てのリポジトリを作って動かします。

手順は次のとおりです。

1. `examples/<slug>/` にワークフローを用意する
2. **実行前にユーザーへ承認を求める**
3. `gh repo create <名前> --private` で使い捨てのリポジトリを作る
4. push して実行する
5. `gh run view --log` で実行のログを取得する
6. 実行の URL、実行日時、ランナーの種類、所要時間を記録する
7. `gh repo delete <名前>` で削除する
8. 削除できたことを確認する

リポジトリの作成と削除は取り消しにくい操作のため、手順 2 の承認を必ず取ります。

実行のログ、本番環境での観測結果、自分のリポジトリでの適用前後の測定値も、検証の証拠として扱います。形式は同じ（日付、環境、条件、観測結果）です。

### 記事本文と検証用ディレクトリの関係

`examples/<slug>/` は書き手が確かめるための作業場所であり、読者の手元には届きません。そのため記事本文には、読者が自分の環境だけで再現できる情報を書きます。ローカルのパス、ディレクトリ名、そこでの起動コマンド、リポジトリの場所は、記事の外に置きます。

検証で得た情報そのものは記事に残します。観測した条件と結果を、そのまま本文に書きます。

- 改善前: 「検証用サンプルでは 40 秒でした」
- 改善後: 「キャッシュを無効にした状態で実行したところ、40 秒でした」

この規則は `write-blog-article`、`article-review`、`tech-review` の 3 つに書きます。

## スキルごとの仕様

5 つのスキルは、このリポジトリの `.agents/skills/skill-creator/`（`.claude/skills/skill-creator` からも参照できます）を使って作ります。SKILL.md の frontmatter の書き方、description の粒度、references の分け方、作ったあとの検証まで、このスキルの手順に従います。

下に書く各スキルの description は方向を示すものです。最終的な文面は `skill-creator` の `scripts/improve_description.py` を通した結果を使います。

### 1. `pick-blog-topic`

**description に書くこと**: 溜めた素材（URL と本文）や作業の記録から、記事にできるかを判定する。素材を渡して書くべきか判断したいとき、作業の記録から切り口を見つけたいとき、次に書くネタを選びたいときに使う。切り口が決まった後の調査と執筆は `write-blog-article` が担う。

**手順**:

1. 入力の種類を判定する（素材か、作業の記録か、記録済みの Issue の一覧か）
2. 素材の固有名詞や数値に紐づけた具体的な質問を 1〜2 問に絞って行う（例: 「7 分かかっていたのは pnpm のインストールですか、依存関係の解決ですか」）
3. 判定する。結果は 3 つ
4. 判定の理由を伝える

**判定の 3 つの結果**:

| 結果 | 条件 | 次の動作 |
|---|---|---|
| 今すぐ書く | 記事の型が決まり、主張を支える材料（動かせるコード、実測値、一次情報）が揃っている | `write-blog-article` へ渡す |
| 材料が足りない | 切り口はあるが、検証や調査が済んでいない | `neta` ラベル付きの GitHub Issue に記録する |
| 見送る | 既出である、材料が足りない、記事にする理由が見つからない | 理由だけを伝える |

**Issue に記録する内容**: 素材へのリンク、そのとき何を見て何を感じたかをそのまま引用した文、記事にするために足りないもの、確かめる必要があること。ユーザーの発言は、そのままの言葉で引用します。

**依存関係**: 他のプラグインのスキルを呼ばずに単独で動きます。深掘りは `write-blog-article` の 1 回目の合意確認で行います。このスキルが担うのは「書くだけの材料があるか」の判定だけです。

### 2. `write-blog-article`

**description に書くこと**: 一次情報を調べ、動かして確かめ、sui-blog の記事の初稿を日本語で書く。記事を書きたい、下書きを作りたいとき、および 4 つの型（変更への追随、手を動かす解説、調査と比較、意見と経験）のいずれかに当てはまるときに使う。すでにある記事の推敲は `article-review` が担う。

**読み込む references**:

| ファイル | 読むタイミング |
|---|---|
| `references/sui-style.md` | 合意確認の前、執筆の前、最後の見直し |
| `references/article-types.md` | 構成を提案する前 |
| `references/research-and-validation.md` | 外部から確かめられる主張やコードを含む場合 |

**手順**:

1. **依頼の内容を把握する**。ユーザーが渡したファイルと作業場所を先に読む。4 つの型のどれかに分類する。質問するのは、読んでも分からなかったことだけにする
2. **1 回目の合意確認**。次の項目について、1 問ずつ質問して決める。質問には推奨する答えとその理由を添える。曖昧な答えには具体例を出して問い返す
   - 想定する読者と、前提にしてよい知識
   - 読者が持ち帰る結論、またはできるようになること
   - 扱う範囲と、範囲の外に置くもの
   - 調査が必要な主張
   - 検証で示す必要のある主張
   - 検証する環境と、成功と判断する条件
   - 記事の型と、見出しの案
   - タイトルの方向、`description` の方向、英小文字の kebab-case による `slug`

   すべて決まったら、決定事項、前提、採らなかった選択肢、残っている疑問をまとめて示し、承認を得る。記事のファイルを作るのは、承認を得た後にする
3. **調べて説明する**。仕様、公式ドキュメント、公式のリポジトリ、リリースノート、Issue と Pull Request を優先する。検索結果の要約ではなく、元の資料を開く。分かったことは、驚いた制約や過去からの変更も含めてユーザーへ説明する。根拠が見つからない場合は、根拠を確認できなかったと書く
4. **証拠を用意する**。「検証の方針」に従う
5. **2 回目の合意確認**。中心となる主張、集めた証拠、制約と互換性、見出しの案、検証の結果、一次情報を示し、承認を得る。軽い記事の場合、ユーザーはこの確認を省略できる
6. **執筆する**。`contents/blog/<YYYY-MM-DD>_<slug>.md` を作る。frontmatter は 8 つのフィールドを埋める

   ```yaml
   title:
   slug:
   date: YYYY-MM-DD
   modified_time: YYYY-MM-DD
   description:
   icon:
   icon_url:
   tags:
     -
   ```

   `description` は要約ではなく、背景、行ったこと、記事で扱う範囲を 1〜3 文で書きます。検索結果や記事の一覧だけで内容が判断できる形にします。本文と同じ「です・ます」の敬体で書き、文は述語で終えます。既存記事の例をそのまま SKILL.md に載せます。

   ```
   GitHub Actions で pnpm v11 を pnpm/action-setup で使うと、セットアップだけで 7 分かかっていました。setup-node のキャッシュと pnpm/setup へ移行して 40 秒まで短くなったので、原因の切り分けと移行の手順を書きます。
   ```

   ```
   Cloudflare Workers の無料プランで日次のバッチを動かしています。1 年運用して見えてきた制限の当たり方と、そこに合わせた設計を書きます。
   ```

   `diagram` と `selfAssessment` は別のスキルで作ります。
7. **見直す**。`article-review` と `tech-review` を使う。両方が使えない環境では `references/sui-style.md` に照らして自分で確認する。日本語と英数字の間のスペースは textlint の検査対象の外にあるため、手で確認する
8. **報告する**。記事のパス、記事の型、想定読者、中心となる主張、一次情報、検証の記録（日付、環境、コマンド、結果）、実行できなかった確認、残っている作業を報告する

   公開、翻訳、コミット、push は、依頼された場合だけ行う

**references の構成**:

- `references/sui-style.md` — 「文章の規範」の全体
- `references/article-types.md` — 「記事の型」の 4 つ
- `references/research-and-validation.md` — 「検証の方針」の全体

### 3. `article-review`

**description に書くこと**: 日本語の記事を、構成、説明の順序、日本語の正しさ、表記の統一、まとめと本文の一致の観点から読み、指摘を返す。下書きの推敲、公開前の確認に使う。技術的な正しさは `tech-review` が確かめる。原稿の書き換えは、依頼された場合だけ行う。

**手順**:

1. 原稿の全体と `references/sui-style.md` を読む
2. 次を見る
   - `title` と `description`
   - 導入で、読者の課題、想定読者、扱う範囲、到達点が分かるか
   - 見出しの順序が、読者の疑問または作業の手順に沿っているか
   - 前提となる概念が、それに依存する概念より先に置かれているか
   - 段落ごとに 1 つのことだけを述べているか
   - 「これ」「それ」が何を指すか明確か
   - コード、画像、リンクの前後に説明があるか
   - 画面や動きの証拠が足りているか。足りない場合、`TODO(media)` のコメントが具体的か
   - 記事本文が、読者の環境だけで再現できる情報で書かれているか
   - `## まとめ` が、本文の結論だけを過不足なく再掲しているか
   - 文体、表記、用語が「文章の規範」に沿っているか
3. 話題テストを全段落の先頭の文と、独立した短い文に適用する
4. 「論証」の各項目を確かめる
5. 「見出しの付け方」を確かめる
6. 「使わない言い回し」を検索する
7. `contents/` で `bun run lint`（textlint）を実行し、その結果も指摘に含める
8. `ai-police` サブエージェントへ原稿を渡し、独立した判断で確認させる
9. 指摘を返す

**指摘の形式**: 重大度の順に並べます。

```
🔴 修正必須: 短い見出し
場所: contents/blog/2026-09-04_pnpm-setup-migration.md:42
読者への影響: 読者が何を誤解するか、何ができないか
修正案: 具体的な置き換え、移動、削除、書き直し
```

重大度は 4 段階です。

| 表示 | 意味 |
|---|---|
| 🔴 修正必須 | 記事が使えない、または読者を誤らせる |
| 🟠 公開前に修正 | 公開までに直すべき構成または日本語の問題 |
| 🟡 改善の提案 | 読みやすさが上がる |
| ⚪️ 任意 | 好みの範囲の調整 |

同じ問題が繰り返し現れる場合は 1 件にまとめます。指摘が 0 件の場合はその旨を伝え、確認できた範囲を書きます。褒める節は、依頼された場合だけ書きます。

**書き換えを依頼された場合**: 意味と書き手の言い回しを保ったまま適用します。主張、技術的な内容、扱う範囲、書き手の意見を変える必要が出た場合は、先に断って承認を得ます。

**references の構成**:

- `references/editorial-checklist.md` — 手順 2 の確認項目
- `references/argument-and-topic-test.md` — 話題テスト、論証、見出しの付け方
- `write-blog-article/references/sui-style.md` を相対パスで読む

### 4. `tech-review`

**description に書くこと**: 記事の技術的な正しさ、一次情報の裏取り、コードが動くか、再現できるか、安全性と互換性を確かめる。公開前の技術的な確認に使う。日本語の推敲は `article-review` が担う。原稿の書き換えは、依頼された場合だけ行う。

**手順**:

1. 確かめる範囲を決める。中心となる主張、バージョンや時期に依存する記述、仕様についての断定、動かす前提のコード、観測結果として書かれている記述、安全性や互換性に関わる助言を洗い出す
2. 一次情報を確かめる。検索結果の要約ではなく元の資料を開く。仕様として定められていること、実装の挙動、過去の議論、書き手の推測、意見を区別する
3. コードを確かめる。記事のコードが検証したソースと一致しているか確かめる。すでにある実行環境を使う。パッケージの追加インストール、外部サービスへの接続、システム設定の変更は、承認を得てから行う
4. 記録と照らす。日付、環境、バージョン、成功と判断する条件、観測結果が書かれているか。未検証の主張に印が付いているか
5. 指摘を返す

**確認項目**:

- 中心となる主張が、一次情報または記録された観測に支えられているか
- バージョンに依存する事実が、現在の情報と照らして正しいか
- 構文、型、API の使い方が、記載されたバージョンで正しいか
- import、依存関係、環境変数、設定、起動の順序が揃っているか
- 期待する出力と、観測した出力が一致しているか
- 集計した表の条件（対象、期間、件数、除外したもの）が書かれているか
- コードに出てくる認証情報が、ダミーの値か使い捨ての値になっているか
- 安全性、アクセシビリティ、互換性、失敗する条件が、必要な箇所で扱われているか
- 過去の議論が、当時の話として書かれているか
- 記事本文が、読者の環境だけで再現できる情報で書かれているか

**指摘の形式**: `article-review` と同じ 4 段階です。1 件ごとに「場所 / 技術的な影響 / 根拠 / 具体的な修正案」を書きます。

**references の構成**:

- `references/technical-checklist.md` — 確認項目

### 5. `japanese-sentence-order`

**description に書くこと**: 日本語の一文の中の語順、読点の位置、入れ子構造を確かめ、読みにくい文を指摘する。ブログ記事、設計書、Issue のコメント、README など、日本語の文章全般に使う。文体と構成の確認は `article-review` が担う。

このスキルが扱うのは**一文の中の語順と読点だけ**です。文体、構成、使わない言い回しの一覧は `sui-style.md` に置いたままにします。範囲を分けることで、規範を 1 か所に置く形を保てます。

**中身の作り方**: `blog-revision/references/japanese-composition.md`（既存スキル、263 行）を `references/sentence-order.md` へ**そのまま引き写します**。このファイルは本多勝一『日本語の作文技術』を元に、悪い例と良い例、ルールを適用しない条件まで含めて書かれています。手元に元の書籍はないため、内容を書き起こし直さず、既存ファイルの本文を維持します。

手を入れてよいのは、見出しの階層を整えることと、ブログ以外の文章にも使えるように記述を一般化することの 2 点だけです。例文はすべて残します。

**含まれる確認項目**:

- 修飾語の順序。長い修飾語を前に、短い修飾語を後に置く
- 節を含む修飾語と、単語だけの修飾語の並び順
- 読点の位置。長い修飾語が 2 つ以上あるとき、その境目に打つ
- 入れ子構造の解消。修飾する語と修飾される語が離れている文を分ける
- 助詞の使い分け（「は」と「が」など）
- 漢字とひらがなの割合

**textlint との分担**: sui-blog の textlint 設定では、一文の長さの検査（`sentence-length`）と助詞の連続の検査（`no-doubled-joshi`）を無効にしてあり、漢字の連続は 10 文字まで許容しています。修飾語の順序、入れ子構造、読点の位置は textlint の検査範囲の外にあります。このスキルはその部分を担当します。

**出力**: 対象の文を引用し、読みにくくなっている理由と、書き換えた文を示します。

## 採用しなかった案とその理由

実装のときに同じ議論をやり直さないための記録です。

### 一文ごとに改行する形式

k16shikano 氏の規範は「一文ごとに改行する」ことを求めています。ただしその理由は、氏の別の文書（記事の書き方）に「差分が見やすくなるように」と明記されているとおり、書籍の編集者が原稿の修正を提案しやすくするためです。ブログには当てはまりません。採用しません。

### 文章の緩急を設計する規範

k16shikano 氏の `cognitive-rhythm-writing` は、文の長短と、断定と迷いの交替で読む速度を作る規範です。ただしこの規範は常体（「〜である」「〜だ」）を前提にしています。常体なら文末が「〜である／〜だ／〜のだ／体言止め」と自然に散りますが、敬体では「ました／ます／ません」しか使えず、同じ文末が続きます。sui-blog は 2026 年の 26 本すべてが敬体のため、この規範を持ち込むと文末が単調になります。採用しません。

この規範から取り込むのは、話題テストだけです。

### 「この記事では」を使わない方針

k16shikano 氏の規範は「本章では〜を扱う」という予告を、内容を足さない言い方として退けています。一方 azukiazusa 氏のブログでは 77.9% の記事が「この記事では」を使っています。sui-blog も `## まとめ` を 96% の記事に置いており、予告と総括を型として使っています。読者が記事の範囲を最初に知る形を採ります。予告を退ける方針は採用しません。

### アテンションライティング

既存の `blog-revision` にあった、冒頭で結論を出す・一文を短くする・情報を小出しにする・装飾を削る、の 4 原則です。

「冒頭で結論を出す」は、記事の型ごとに導入を決める方針と両立しません。残る 3 つは他の規則と重なります。「一文を短く」は一文一義と入れ子構造の解消に、「装飾を削る」は使わない言い回しの一覧に含まれます。全体を採用しません。

### SCQ と共感を組み合わせた導入の設計

既存の `blog-structuring` にあった、状況・complication・問いの順に並べ、読者に共感してから一部を裏切る導入の設計です。「ここですぐに解決策を提示しない」という指示が、アテンションライティングの「冒頭で結論を出す」と反対の方向を向いており、どちらに従うかの判断ができない状態を作っていました。記事の型ごとに導入を決める方針に置き換えます。

### 検証用プロジェクトを Git で管理する案

記事を更新するときには対象のバージョンが変わっているため、古い検証用プロジェクトはそのまま使えず作り直しになります。残るのは古い依存関係だけです。また Renovate と CI の対象に入ります。`.gitignore` に入れます。

### スキルの分割を執筆の工程に合わせる案

現在の 7 スキルの分け方です。工程で分けると、工程をまたいで適用される規則が複数のスキルに分散し、指示の食い違いが起きます。実際に食い違いが 1 件、同じ文章の重複が 4 件発生していました。役割で分ける形に変更します。

### 深掘りを外部のスキルに任せる案

既存の `blog-triage` は、ネタの深掘りを別プラグインの `grilling` スキルに任せ、それが入っていなければ停止する作りでした。`grilling` は決定の妥当性を問い詰めるスキルで、記事の切り口を決める作業とは目的が違います。また外部への依存があると、それが入っていない環境でネタの選別が止まります。深掘りは `write-blog-article` の 1 回目の合意確認で行います。

### `diagram` と `selfAssessment` を執筆スキルが作る案

`selfAssessment`（4 択の理解度確認）は `quiz` スキルが既にあります。`diagram`（記事の内容を図として表す構造化データ）も記事本文とは別の作業です。執筆スキルに含めると、記事を書き終えた後の工程が長くなります。含めません。

## 実装の手順

1. `plugins/blog-writing-skills/skills/` 配下の既存 7 ディレクトリを、作業用の一時ディレクトリ（例: `/tmp/blog-skills-old/`）へ移す。引き写す元のファイルをこの間ずっと読めるようにするため、この時点では削除しない
2. `.agents/skills/skill-creator/SKILL.md` の手順に従って、5 つのスキルのディレクトリと SKILL.md、references を作る。「既存スキルからの引き写し方」の表に挙げた節と `japanese-composition.md` は、一時ディレクトリから本文をそのまま持ってくる
3. `plugins/blog-writing-skills/.claude-plugin/plugin.json` と `.codex-plugin/plugin.json` のバージョンを上げる（`bun run version-bump blog-writing-skills major`）
4. `plugins/blog-writing-skills/README.md` を、5 つのスキルの一覧と使い分けの表に書き換える
5. `.claude-plugin/marketplace.json` と `.agents/plugins/marketplace.json` のエントリを確認し、必要なら説明文を更新する
6. `bun run check` を実行する
7. sui-blog 側の `.gitignore` に `examples/` を追加する
8. 引き写しが済んだことを確認してから、手順 1 の一時ディレクトリを削除する
